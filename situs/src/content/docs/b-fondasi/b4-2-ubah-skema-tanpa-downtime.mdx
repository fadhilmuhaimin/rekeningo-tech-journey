## Inti

Kode lama dan baru selalu berjalan bersamaan, dan app lama bertahan berbulan-bulan. Jadi skema diubah bertahap: tambah, pindahkan, baru hapus.

## Lihat sendiri

Kolom `telp` diganti `no_hp`. Budi memakai app v1.4 di HP dan v1.5 di tablet. SQL dan model Dart di widget ini direkam dari PostgreSQL 17 dan Dart 3 sungguhan.

## Kenapa ini ada

Rekeningo v1.5 merapikan nama field. Raka ingin `telp` menjadi `no_hp`, supaya sama dengan form di app baru.

Di Tahap 1, Raka cukup menulis satu migration `RENAME COLUMN` lalu deploy. Downtime beberapa menit masih bisa diterima, dan semua penguji memakai build yang sama.

Di Tahap 2 keadaannya lain. Sekitar seribu user memakai app dari Play Store dan App Store, dan tidak semua update app. Sebagian user masih menjalankan v1.4, yang mengharapkan field `telp`. Raka tidak bisa memaksa mereka update hari ini.

Ada juga masalah kedua yang lebih singkat. Saat deploy, instance API lama dan baru berjalan bersamaan. Migration yang mengganti nama kolom membuat semua query instance lama gagal.

## Cara kerjanya

Polanya disebut **expand and contract**, atau parallel change ([Fowler](https://martinfowler.com/bliki/ParallelChange.html)). Setiap fase adalah deploy terpisah:

| Fase | Database | API | App lama (v1.4) |
|---|---|---|---|
| 1. Expand | Tambah kolom `no_hp`, boleh kosong | Tetap memakai `telp` | Normal |
| 2. Tulis ganda | – | Menulis ke `telp` **dan** `no_hp` | Normal |
| 3. Backfill | Isi `no_hp` untuk baris lama, per batch | – | Normal |
| 4. Baca baru | – | Membaca `no_hp`, response tetap membawa `telp` | Normal |
| 5. Contract | Hapus `telp` | Berhenti menulis dan mengirim `telp` | Sudah tidak dipakai |

Fase 5 baru aman setelah tidak ada lagi yang membaca kolom atau field lama. Untuk API, itu berarti metric request dari v1.4 sudah mendekati nol, atau versi minimum sudah dinaikkan. Caranya ada di [[E1]].

**Menambah aman, menghapus tidak.** App lama mengabaikan field yang tidak ia kenal, jadi `no_hp` tambahan tidak mengganggu. Field yang hilang membuat app lama crash. Rekaman di widget menunjukkannya: `j['telp'] as String` gagal karena nilainya `null`.

**"Instan" di database tidak berarti tanpa risiko.** Dokumentasi PostgreSQL menyebut `ADD COLUMN` tanpa `DEFAULT` tidak menulis ulang tabel ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)).

Tapi hampir semua bentuk `ALTER TABLE` butuh lock `ACCESS EXCLUSIVE`. Lock itu harus menunggu transaction lain di tabel yang sama selesai. Selama menunggu, query baru di tabel itu ikut tertahan di belakangnya. Karena itu pasang [`lock_timeout`](https://www.postgresql.org/docs/current/runtime-config-client.html) dan coba ulang:

<Snippet file="labs/b4-skema/output/lock-timeout.txt" title="Output rekaman: labs/b4-skema/output/lock-timeout.txt" />

**Backfill per batch.** Satu `UPDATE` untuk semua baris memegang lock baris sampai selesai dan membuat transaction yang sangat besar. Batch kecil membuat setiap transaction pendek. Di rekaman: 1.000, 1.000, 499, lalu 0 baris.

## Di stack lain

**Skenario:** fase 1 (expand) dan fase 5 (contract) untuk kolom `no_hp`. SQL di tab pertama dijalankan di lab. Tab lain hanya dicek ke dokumentasi, tidak dijalankan.

Yang sama di semua stack: expand dan contract adalah **dua migration terpisah**, di dua deploy yang berbeda. Yang berbeda: apakah migration dibungkus transaction, dan di mana backfill ditulis.

<Fragment slot="t1">

*Tidak dijalankan. Dicek ke [Laravel: Migrations](https://laravel.com/docs/12.x/migrations) dan [chunkById](https://laravel.com/docs/12.x/queries#chunking-results).*

<Snippet lang="php" code={`// 2026_10_06_000007_tambah_no_hp.php   (deploy 1)
Schema::table('akun', function (Blueprint $table) {
    $table->string('no_hp')->nullable();
});

// Backfill: di command terpisah, per batch berdasarkan primary key
DB::table('akun')->whereNull('no_hp')->chunkById(1000, function ($baris) {
    foreach ($baris as $b) {
        DB::table('akun')->where('id', $b->id)->update(['no_hp' => $b->telp]);
    }
});`} />

<p class="bb-beda">**Yang berbeda di stack ini:** `renameColumn` tersedia dan menggoda. Itu yang menyebabkan crash di varian widget.</p>

</Fragment>
<Fragment slot="t2">

*Tidak dijalankan. Dicek ke [Django: Migrations](https://docs.djangoproject.com/en/stable/topics/migrations/) dan [Migration operations](https://docs.djangoproject.com/en/stable/ref/migration-operations/).*

<Snippet lang="python" code={`# 0007_akun_no_hp.py   (deploy 1)
class Migration(migrations.Migration):
    dependencies = [("rekening", "0006_akun_telp")]
    operations = [
        migrations.AddField(model_name="akun", name="no_hp",
                            field=models.TextField(null=True)),
    ]`} />

<p class="bb-beda">**Yang berbeda di stack ini:** di PostgreSQL, Django menjalankan seluruh migration dalam satu transaction. Backfill besar lewat `RunPython` di migration yang sama akan jadi satu transaction raksasa. Pisahkan backfill, atau pakai `atomic = False` dan batch sendiri.</p>

</Fragment>
<Fragment slot="t3">

*Tidak dijalankan. Dicek ke [Supabase: Database migrations](https://supabase.com/docs/guides/deployment/database-migrations).*

<Snippet lang="sql" code={`-- supabase/migrations/20261006000007_tambah_no_hp.sql
ALTER TABLE akun ADD COLUMN no_hp text;`} />

<p class="bb-beda">**Yang berbeda di stack ini:** app sering membaca tabel langsung lewat API otomatis. Nama kolom adalah nama field di JSON. Rename kolom langsung mengubah response untuk semua versi app.</p>

## Trade-off: kapan pakai apa

| Opsi | Kelebihan | Kekurangan |
|---|---|---|
| Rename langsung + downtime | Satu migration, cepat ditulis | App lama crash, request gagal selama deploy |
| Expand → migrate → contract | Tidak ada yang crash, bisa dibatalkan di setiap fase | 3–5 deploy, butuh minggu sampai app lama hilang |
| Biarkan nama lama selamanya | Nol risiko | Nama yang membingungkan menumpuk jadi technical debt |

Rule of thumb: kalau datanya dibaca app yang tidak bisa kamu paksa update, pakai expand-contract. Kalau hanya dibaca kode server yang di-deploy bersamaan, satu migration cukup.

## Cek diri

**1.** Susun urutannya: (a) hapus kolom `telp`, (b) backfill `no_hp`, (c) tambah kolom `no_hp`, (d) API membaca `no_hp`, (e) API menulis ke dua kolom.

<details class="success">
<summary>Jawaban</summary>

c → e → b → d → a. Tulis ganda (e) harus sebelum backfill (b). Kalau terbalik, baris yang berubah setelah backfill dan sebelum tulis ganda akan punya `no_hp` yang salah.

</details>

**2.** Jelaskan kenapa `ALTER TABLE akun ADD COLUMN no_hp text`, yang selesai dalam 0,8 ms di lab, tetap bisa membuat app terasa macet.

<details class="success">
<summary>Jawaban</summary>

Perintah itu butuh lock `ACCESS EXCLUSIVE` pada tabel. Kalau ada transaction panjang yang sedang membaca tabel itu, ALTER harus menunggu. Selama menunggu, query baru di tabel yang sama ikut antre di belakang ALTER. Dengan `lock_timeout`, ALTER menyerah dan bisa dicoba ulang, bukan menahan semua request.

</details>

**3.** App v1.4 tidak dipakai lagi menurut metric. Raka langsung menghapus field `telp` dari response dan kolom `telp` di migration yang sama. Apa risikonya kalau deploy itu harus di-rollback?

<details class="success">
<summary>Jawaban</summary>

Kode versi sebelumnya masih membaca kolom `telp`, padahal kolomnya sudah hilang. Rollback kode jadi gagal. Karena itu contract di database biasanya dijalankan satu deploy setelah kode berhenti memakai kolom lama.

</details>

## Saat me-review kode AI, cek ini

- [ ] Tidak ada `RENAME COLUMN`, `DROP COLUMN`, atau perubahan tipe pada kolom yang masih dibaca kode atau app yang sedang berjalan.
- [ ] Kolom baru boleh kosong, atau memakai `DEFAULT` yang tidak volatile.
- [ ] Ada `lock_timeout` sebelum `ALTER TABLE` di tabel yang sibuk.
- [ ] Backfill per batch, terpisah dari migration skema.
- [ ] Response API hanya menambah field. Field lama dihapus setelah versi minimum app dinaikkan.
