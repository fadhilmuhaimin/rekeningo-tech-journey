## Inti

Sesudah pindahan, vendor tetap melihat satu alamat, dan nilai secret tidak tersimpan di state OpenTofu.

<Rantai data={intiDiagram} ringkas />

Di Rekaman lab ([Label sumber](/cara-pakai/#label-sumber)) `alamat.txt` bagian A, vendor tiruan hanya menerima alamat yang ada di allowlist, yaitu daftar alamat sumber yang boleh memanggilnya. Host baru menyala dengan alamat lain. Tiga pengajuan sesudah pindahan dijawab 403 lima kali per pekerjaan, jadi 15 penolakan dan tiga pengajuan `gagal`.

Di bagian B, proxy keluar didaftarkan sekali. Proxy keluar adalah program perantara dengan alamat tetap, yang dilewati panggilan keluar. Tiga pengajuan sesudah pindahan lulus tanpa satu penolakan.

OpenTofu adalah alat IaC (infrastructure as code): ia membuat infrastruktur dari file konfigurasi, dan mencatat apa yang sudah dibuatnya di file state. Di `state.txt` bagian A, password dan kunci yang ditulis di konfigurasi ikut masuk state, walau keluaran CLI menulis `(sensitive value)`. Di bagian B, konfigurasi hanya menulis alamat dan path secret manager, yaitu layanan penyimpan secret. Nilainya dibaca service sendiri saat runtime, yaitu saat service berjalan, jadi state tidak memuatnya.

### Kenapa ini ada

[[t4-m34]] menulis tiga akibat satu pindahan: alamat keluar berubah, nilai secret tertulis di state, dan staging memakai kunci produksi (Ilustrasi, bukan hasil sistem). Halaman ini menulis apa yang mencegah ketiganya.

Satu VPS yang memegang data, file, dan secret adalah titik gagal tunggal yang sengaja diterima ADR 26 dan ADR 33 ([[t3-dua-instance]], [[t3-adr-33]]). ADR 11 menaruh nilai asli hanya di `.env` VPS ([[t1-secret]]). Begitu uang publik masuk ([[t4-prd]]), satu mesin yang hilang atau diretas membawa data dan secret sekaligus.

### Cara kerjanya

**Alamat keluar tetap.** Sebagian vendor hanya menerima panggilan dari alamat yang sudah didaftarkan. Di lab, vendor tiruan memeriksa alamat peer TCP, bukan header seperti `X-Forwarded-For`, karena header diisi client (README lab dan `TestSumberHanyaAlamatPeerBukanHeader` di `testing.txt`).

Host baru dinyalakan sebelum host lama dimatikan, dan rekaman memeriksa bahwa alamatnya berbeda. Hasilnya di bagian A:

<Snippet file="labs/t4-infra/output/alamat.txt" lines="39:43" title="Rekaman lab: labs/t4-infra/output/alamat.txt (bagian A, sesudah pindahan)" />

Tiap pekerjaan memakai lima percobaan atas jawaban 403 yang tidak akan berubah: tiga pekerjaan kali lima percobaan menjadi 15 penolakan. Vendor sehat, dan penyebabnya alamat sumber. Breaker ADR 36 tidak menolong jawaban 403, dan itu bahan [[t4-m34]], bukan halaman ini.

Proxy keluar memindahkan pendaftaran dari alamat host ke alamat proxy. Di lab, proxy meneruskan HTTP biasa hanya ke tujuan yang didaftarkan. Aplikasi tidak berubah: client HTTP Go membaca `HTTP_PROXY` dari lingkungan ([net/http: ProxyFromEnvironment](https://pkg.go.dev/net/http#ProxyFromEnvironment), Go 1.27.3, dibuka 2026-10-30; lab memakai Go 1.27.1). Hasilnya di bagian B:

<Snippet file="labs/t4-infra/output/alamat.txt" lines="80:84" title="Rekaman lab: labs/t4-infra/output/alamat.txt (bagian B, sesudah pindahan)" />

Di rekaman itu tiga alamat berbeda satu sama lain: host lama, host baru, dan proxy. Vendor hanya melihat proxy.

Batasnya tertulis di README lab. Proxy keluar adalah titik gagal tunggal baru, dan matinya tidak direkam. CONNECT untuk HTTPS dijawab 501 dan vendor tiruan tidak memakai TLS, jadi HTTPS lewat proxy Tidak dijalankan.

Di cloud, padanannya NAT dengan IP tetap. Dokumentasi Amazon VPC menulis bahwa NAT gateway publik wajib memegang satu Elastic IP sejak dibuat ([NAT gateways](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html), dibuka 2026-10-30). NAT cloud Tidak dijalankan di lab.

Satu hal yang mudah terlewat dibaca dari kode, bukan dijalankan. Fungsi `klien.Baru` membuat client tanpa transport sendiri, jadi `HTTP_PROXY` untuk vendor juga berlaku bagi pembacaan OpenBao oleh service yang sama. Dokumentasi Go hanya menulis pengecualian untuk host `localhost`, jadi alamat OpenBao lain perlu masuk `NO_PROXY`. Ini Tidak dijalankan: dibaca dari kode dan dokumentasi.

**IaC dan state.** IaC menulis infrastruktur sebagai file konfigurasi. Alat IaC membandingkan konfigurasi dengan state, lalu menjalankan perubahan lewat provider, yaitu plugin untuk satu jenis layanan.

Di lab, provider-nya `random` dan `local`, bukan provider cloud. Tabel ini menulis tiga cara menaruh secret, dengan Rekaman lab `state.txt`:

| Bagian | Cara di konfigurasi | State memuat nilainya | Penanda sensitif di state |
|---|---|---|---|
| A | `random_password` dan variabel `kunci_gateway` dipakai `local_file` | ya, tiga atribut | terisi |
| B | `local_file` hanya menulis alamat OpenBao dan path | tidak | tidak berlaku, tidak ada nilai |
| C | data source `local_sensitive_file` membaca file rahasia | ya | kosong |

Konfigurasi bagian A menulis nilai ke dua resource:

Konfigurasi bagian B tidak menyentuh nilainya. Ia hanya menulis tempat service mengambilnya:

<Snippet file="labs/t4-infra/tofu/rahasia-runtime/main.tf" lines="20:23" lang="hcl" title="labs/t4-infra/tofu/rahasia-runtime/main.tf" />

Bagian C memakai provider `local` sebagai pengganti data source pembaca secret manager. Bahwa data source provider Vault atau OpenBao berperilaku sama [perlu verifikasi]: provider itu tidak dijalankan.

Dokumentasi OpenTofu menulis bahwa state lokal adalah file JSON teks biasa, dan menyuruh state diperlakukan sebagai data sensitif ([sensitive data in state](https://opentofu.org/docs/language/state/sensitive-data/), dibuka 2026-10-30). Nilai sensitif tetap tersimpan sebagai teks di state dan plan, sedangkan nilai ephemeral tidak disimpan di keduanya ([ephemerality](https://opentofu.org/docs/language/ephemerality/), dibuka 2026-10-30). Enkripsi state dan plan serta nilai ephemeral Tidak dijalankan di lab: state lab adalah file lokal teks biasa.

Pilihan alat ada di lisensi dan rilisnya. Lisensi OpenTofu dan OpenBao adalah MPL-2.0 (file LICENSE di repositori masing-masing, dibuka 2026-10-30). Terraform v1.17.1 dan Vault v2.2.1 memakai Business Source License. HashiCorp mengumumkan perubahan itu dari MPL 2.0 ke BSL v1.1 pada 10 Agustus 2023 ([HashiCorp adopts Business Source License](https://www.hashicorp.com/en/blog/hashicorp-adopts-business-source-license), dibuka 2026-10-30).

Teks lisensi Terraform dan Vault mengizinkan penggunaan produksi, kecuali menawarkannya ke pihak ketiga sebagai layanan hosted atau embedded yang bersaing dengan versi berbayar IBM. Memakai Terraform untuk infrastruktur sendiri tidak masuk kalimat larangan itu, tetapi halaman ini bukan penilaian hukum [perlu verifikasi: tinjauan hukum PT]. Terraform dan Vault hanya dibandingkan, tidak dijalankan.

**Secret manager dan rotasi.** Lab memakai OpenBao v2.7.2 dalam mode dev. Mode dev menyimpan data di memori, kehilangan data di tiap restart, dan dokumentasinya melarangnya di produksi ([dev server](https://openbao.org/docs/concepts/dev-server/), dibuka 2026-10-30). Rekaman A membuktikannya: sesudah container dihentikan dan dinyalakan lagi, secret yang tadi ditulis dijawab 404.

Service pembayaran membaca secret lewat token baca-saja, yaitu token yang hanya boleh membaca satu path. Percobaan menulis dijawab 403, dan token yang tidak dikenal membuat service tidak menyala (`rotasi.txt` bagian B). Pembacaan yang gagal tidak mengganti daftar yang sudah ada:

Dokumen secret berisi dua nilai, `sekarang` dan `lama`. Selama dua nilai itu ada, masa tumpang tindih berlaku: kabar bertanda tangan nilai lama masih diterima. Di bagian C, operator menulis versi 2, dan service yang sama membaca dua rahasia tanpa deploy:

<Snippet file="labs/t4-infra/output/rotasi.txt" lines="29:32" title="Rekaman lab: labs/t4-infra/output/rotasi.txt (bagian C, sesudah rotasi)" />

Kode pembaca membentuk daftar rahasia dari dua nilai itu:

<Snippet file="labs/api-t4/internal/rahasia/bao.go" lines="109:112" lang="go" title="labs/api-t4/internal/rahasia/bao.go" />

Urutannya menentukan. Bagian D membalik urutan: gateway beralih ke rahasia baru sebelum operator menulisnya, dan kabarnya ditolak 401 sampai service membaca (`rotasi.txt` bagian D). Gateway mengulang kabar yang tidak dijawab 2xx ([[t4-m30]]). Urutan aman adalah tulis ke OpenBao, tunggu service membaca, baru penanda tangan beralih. 

Jeda baca bawaan service 30 detik (Asumsi), dan lab memakai 50 ms. Pada puncak ada 0,579 top-up per detik (Asumsi: 20.000 × 0,25 ÷ 86.400 × 10). Jendela itu menolak paling banyak 0,579 × 30 = 17,37 kabar, atau ±17. Itu Hitungan: hasil rumus dari angka yang tertulis di halaman ini, dan karena memakai Asumsi hasilnya Asumsi.

Saat OpenBao mati, service memakai pembacaan terakhir tanpa batas umur dan menghitung kegagalan beruntun. Setelah OpenBao menyala lagi dengan memori kosong, kabar bertanda tangan secret yang hilang tetap diterima:

**Staging dan produksi terpisah.** Token staging membaca secret staging dengan jawaban 200, dan membaca atau menulis secret produksi dengan jawaban 403 (`staging.txt` bagian A). Pemisahan di lab adalah kebijakan path dan token pada satu instance. Instance atau akun terpisah Tidak dijalankan, dan rekomendasi OpenBao tentang itu belum dicek [perlu verifikasi].

Kunci produksi di staging adalah Ilustrasi, tetapi pemindainya direkam atas dua file contoh. Keluarannya memuat file, nomor baris, dan alasan, tanpa nilai kunci:

<Snippet file="labs/t4-infra/output/staging.txt" lines="16:19" title="Rekaman lab: labs/t4-infra/output/staging.txt (bagian B, pemindai)" />

Baris lebih panjang dari 1 MiB dilaporkan sebagai temuan, dan file yang tidak ada menghasilkan exit 2, bukan file yang tampak bersih. Pemindai hanya melihat file yang diberikan. Nilai yang diubah bentuknya, seperti base64, tertangkap hanya bila bentuk itu ada di daftar sidik (README lab). Menjalankannya atas seluruh konfigurasi staging dan state IaC adalah pekerjaan pipeline di [[t4-tim-infra]].

**Yang dijawab hosting terkelola, dan yang tidak.** Data, file, dan secret tidak lagi mati bersama satu VPS, dan mesin pengganti dibuat dari IaC. App tetap berhenti selama mesin diganti. VPS kedua tetap ditunda ADR 33, karena PRD v4 tidak menulis batas waktu pulih atau jendela kehilangan data ([[t4-prd]]).

Pembanding: `pg_dump` harian berjendela sampai 24 jam. Satu hari punya 20.000 × 3 = 60.000 transaksi dan 20.000 × 0,25 = 5.000 top-up. Jumlahnya 65.000 kejadian uang per hari (Hitungan atas Asumsi: 100.000 user, 20% aktif). Jendela layanan terkelola menurut penyedia belum diketahui [perlu verifikasi: penyedia dipilih saat halaman ditulis], dan hosting terkelola serta failover Tidak dijalankan.

### ADR 39: layanan terkelola untuk data, file, dan secret, IaC, dan alamat keluar tetap

**Kebutuhan.** [[t4-m34]] menunjukkan tiga akibat pindahan yang tidak tertulis di kode. Pemicu lainnya PRD v4: PT berdiri sendiri, dengan infrastruktur, kredensial, dan akses data sendiri ([[t4-prd]]). Satu VPS dengan `.env` adalah titik gagal tunggal yang ADR 26 dan ADR 33 terima, dan uang publik mengubah artinya.

Pendaftar baru datang 1.000 per hari (Asumsi). Alamat keluar yang tertunda dua hari kerja (Asumsi) menahan 2 × 1.000 = 2.000 pendaftar (Hitungan atas dua Asumsi, pendaftaran dihitung rata tiap hari).

**Status:** diterima sesudah M34. Menjawab sebagian titik gagal tunggal ADR 26. Opsi A di bawah adalah ADR 11 yang dipakai sampai M34.

| | A. Satu VPS dan `.env` | B. Dua VPS, replikasi buatan sendiri | C. Layanan terkelola, IaC, dan alamat tetap | D. Secret manager sendiri di VPS |
|---|---|---|---|---|
| Cara kerja | Data, file, dan secret di satu mesin. Nilai secret di `.env` mesin itu | Dua mesin, PostgreSQL direplikasi sendiri | Data, file, dan secret di layanan terkelola. Mesin dibuat dari IaC. Alamat keluar lewat proxy atau NAT | OpenBao atau Vault dijalankan di VPS yang sama atau kedua |
| Kelebihan | Tidak ada pekerjaan baru. Dijaga ADR 11 | Menutup titik gagal tunggal data | Data, file, dan secret tidak mati bersama satu mesin. Rotasi tanpa deploy | Rotasi tanpa deploy, dan kontrol penuh atas alatnya |
| Kekurangan | M34 dan uang publik. `.env` hilang atau terbaca pihak lain bersama mesin | Operasi replikasi dan failover milik tim sendiri, dan ADR 33 menundanya | App tetap berhenti saat mesin diganti. Biaya layanan belum dihitung | Secret manager ikut menjadi titik gagal. Mode dev hanya untuk lab |
| Biaya operasional | Nol, sampai pindahan atau kebocoran | Dua mesin, replikasi, dan giliran jaga | Satu repo IaC, satu proxy atau NAT, dan akun cloud PT | Penyimpanan yang bertahan, unseal, dan token per service |
| Bukti | Rekaman `alamat.txt` A dan `state.txt` A | Tidak dijalankan: dibaca dari naskah | Rekaman `alamat.txt` B, `state.txt` B, `rotasi.txt` C. Layanan terkelola Tidak dijalankan | Rekaman `rotasi.txt` A dan E atas mode dev. Produksi Tidak dijalankan |

**Keputusan: opsi C.** Enam aturan:

1. PostgreSQL, penyimpanan objek, dan secret manager berada di layanan terkelola di akun cloud PT (Tidak dijalankan: lab memakai tiruan di Compose). Mesin app dibuat dari IaC dengan OpenTofu.
2. Konfigurasi IaC tidak memuat nilai secret. Yang membaca nilainya adalah service saat runtime, bukan OpenTofu, karena data source yang membaca nilai juga menyimpannya di state. State disimpan di backend terenkripsi dengan akses terbatas (Tidak dijalankan: state lab adalah file lokal teks biasa).
3. Secret staging dan produksi terpisah. Di lab keduanya satu instance mode dev dengan dua path dan dua kebijakan, dan instance terpisah Tidak dijalankan. Pemindai kunci produksi memeriksa konfigurasi staging.
4. Rotasi lewat secret manager tanpa deploy: tulis dulu, tunggu service membaca, baru penanda tangan beralih, lalu akhiri tumpang tindih. Rotasi karena kebocoran selesai sesudah versi lama dihancurkan.
5. Alamat keluar tetap lewat proxy keluar atau NAT dengan IP tetap, didaftarkan sekali ke vendor yang menuntut allowlist.
6. Alat: OpenTofu v1.13.2 dan OpenBao v2.7.2, yang dijalankan di lab. Terraform v1.17.1 dan Vault v2.2.1 hanya dibandingkan. README lab menulis Terraform v1.17.0, dan v1.17.1 terbit 2026-10-28.

**Kenapa C, bukan A, B, atau D.**

- **A ditolak** karena pindahan membawa alamat, nilai secret, dan state yang tidak tertulis di kode, dan satu mesin mati membawa data dan secret bersamanya.
- **B ditolak** karena replikasi PostgreSQL buatan sendiri menutup titik gagal tunggal data dengan operasi yang ditunda ADR 33. Pemicu ADR 33 belum ada di PRD.
- **D ditolak** untuk Rekeningo: secret manager di VPS yang sama mati bersama mesinnya, dan produksi butuh penyimpanan yang bertahan dan unseal (Tidak dijalankan). Opsi ini tetap masuk akal bila data harus tinggal on-prem.

**Kasus industri: CircleCI.** Laporan insiden CircleCI menulis bahwa malware di laptop satu karyawan mencuri session cookie. Penyerang lalu mengambil environment variable, token, dan key pelanggan dari sebagian database dan store. CircleCI meminta pelanggan merotasi secret mereka, termasuk token OAuth, token API proyek, dan SSH key ([laporan insiden](https://circleci.com/blog/jan-4-2023-incident-report/), 12 Januari 2023, dibuka 2026-10-30).

Batasnya: satu vendor CI yang memegang secret pelanggan, bukan sistem uang. Laporan itu menulis bahwa data tersimpan terenkripsi, tetapi penyerang mengambil kunci enkripsi dari proses yang berjalan. Pelajaran untuk Rekeningo adalah penalaran: rotasi harus bisa dijalankan tanpa deploy dan selesai dengan menghancurkan versi lama.

**Pre-mortem.** Bayangkan keputusan ini gagal 6 bulan lagi. Tiga penyebab yang paling mungkin:

1. Service tetap menerima secret yang sudah dicabut. Pembacaan terakhir dipakai tanpa batas umur, dan alert atas kegagalan beruntun belum ada (`rotasi.txt` bagian E). Pencegahannya batas umur dan alert. Keduanya belum dibangun, jadi ini pertanyaan terbuka.
2. State IaC memuat nilai secret karena satu resource atau data source menyentuhnya (`state.txt` bagian A dan C). Pencegahannya aturan 2, review PR atas konfigurasi, dan backend terenkripsi (Tidak dijalankan).
3. Alamat tetap menjadi titik gagal baru yang terlupa. Proxy mati, atau hosting berpindah lagi dan alamat baru belum didaftarkan. Matinya proxy tidak direkam. Pencegahannya daftar vendor yang memakai allowlist di repo IaC dan pemeriksaan sebelum pindah (Ilustrasi: belum dibuat).

**Kapan keputusan ini salah.**

- Saat hosting berpindah lagi tanpa alamat tetap: 2 hari kerja × 1.000 pendaftar per hari = 2.000 pendaftar tertunda (Hitungan atas dua Asumsi).
- Saat biaya layanan terkelola melebihi biaya mengoperasikan sendiri, atau data harus tinggal on-prem. Halaman ini tidak menghitung biaya, jadi belum ada angka pembandingnya.
- Saat dukungan provider OpenTofu tertinggal dari yang dibutuhkan. Jalan keluarnya Terraform atau Vault, sesuai lisensinya.
- Saat PRD menuntut app tetap hidup bila satu mesin mati. Itu instance kedua, yang ADR 33 tunda, dengan pembanding 65.000 kejadian uang per hari dalam satu jendela `pg_dump` (Hitungan atas Asumsi).
- Saat jeda baca service melebihi ±17 kabar ditolak per rotasi urutan terbalik (0,579 × 30; Hitungan atas Asumsi).

**Yang akan merevisinya.** [[t4-tim-infra]] menjalankan pemindai atas seluruh konfigurasi staging dan state IaC di pipeline. Batas umur pembacaan secret, instance OpenBao terpisah, dan proxy kedua belum dijadwalkan. BFF terpisah dari halaman lama [[B11.2]] tidak dibahas di sini, dan [[t4-adr-45]] menyebutnya.

### Cek diri

**1.** Vendor sehat menolak host baru dengan 403. Apa yang berubah di bagian B rekaman, dan apa yang didaftarkan?

<details class="success">
<summary>Jawaban</summary>

Yang didaftarkan sekali adalah alamat proxy keluar, bukan alamat host. Host baru memakai `HTTP_PROXY` yang sama, vendor hanya melihat proxy, dan tiga pengajuan sesudah pindahan lulus tanpa penolakan (`alamat.txt` bagian B).

</details>

**2.** Konfigurasi OpenTofu menulis `random_password` dan variabel yang dipakai satu resource. CLI menulis `(sensitive value)`. Apakah state memuat nilainya?

<details class="success">
<summary>Jawaban</summary>

Ya. Tanda sensitif hanya menyembunyikan nilai dari keluaran CLI, dan state tetap menyimpannya sebagai teks (`state.txt` bagian A; dokumentasi OpenTofu).

</details>

**3.** Operator menulis versi baru secret di OpenBao, lalu gateway beralih. Kabar gateway ditolak 401. Apa urutan yang aman?

<details class="success">
<summary>Jawaban</summary>

Operator menulis ke OpenBao lebih dulu, service membaca, dan baru penanda tangan beralih. Jeda baca bawaan 30 detik adalah Asumsi, jadi jendela terbalik menolak sampai ±17 kabar pada laju puncak (`rotasi.txt` bagian D).

</details>

**4.** Rotasi sudah menulis dokumen tanpa `lama`, dan service menolak kabar bertanda tangan secret lama. Apakah secret lama sudah mati?

<details class="success">
<summary>Jawaban</summary>

Belum. Versi lama dokumen tetap terbaca token service sampai operator menjalankan destroy (`rotasi.txt` bagian C). Rotasi karena kebocoran selesai sesudah destroy.

</details>

**5.** Data, file, dan secret sudah di layanan terkelola. Apa yang masih berhenti saat mesin app diganti, dan keputusan mana yang menundanya?

<details class="success">
<summary>Jawaban</summary>

App berhenti selama mesin diganti. VPS kedua ditunda ADR 33, karena PRD v4 belum menulis batas waktu pulih atau jendela kehilangan data.

</details>

### Saat me-review kode AI, cek ini

- [ ] Konfigurasi IaC tidak menyentuh nilai secret lewat variabel, resource, atau data source. Yang ada hanya alamat dan path.
- [ ] Service membaca secret saat runtime dengan token yang hanya boleh membaca path miliknya.
- [ ] Panggilan keluar ke vendor yang memakai allowlist lewat proxy atau NAT yang sudah didaftarkan, dan `NO_PROXY` memuat alamat layanan internal.
- [ ] Pembacaan secret yang gagal tidak diam-diam memakai nilai lama tanpa batas umur dan tanpa alert.
- [ ] Rotasi menulis ke secret manager lebih dulu, menunggu service membaca, baru mengganti penanda tangan.
- [ ] Staging tidak membaca path produksi, dan pemindai kunci produksi ikut CI.
