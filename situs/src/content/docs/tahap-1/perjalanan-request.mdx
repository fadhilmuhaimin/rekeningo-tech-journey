## Inti

Tap Bayar menghasilkan satu HTTP request yang melewati handler, logika bisnis, dan akses data, lalu kembali sebagai response.

<Rantai data={duaKemungkinan} ringkas />

Setiap lapisan boleh menghentikan perjalanan, dan app harus siap untuk tiap jawaban. Handler menolak request tanpa token atau dengan token yang tidak berlaku dengan `401`, dan format yang salah dengan `400`. Logika bisnis menolak saldo kurang dengan `422`. Error yang tidak terduga di akses data berakhir sebagai `500`.

Satu kegagalan tidak membawa status apa pun: response hilang di jalan. Di rekaman lab, server sudah menyimpan pembayaran, HP Budi menampilkan gagal, dan Bayar kedua tercatat sebagai pembayaran kedua. Karena itu tombol "Coba lagi" berbahaya untuk aksi yang memindahkan uang.

2. Apa arti status `201`, `400`, dan `401`?

### Kenapa ini ada

Minggu pertama uji coba. Raka menulis endpoint bayar pertamanya. Selama ini, di sisi Flutter, ia hanya menulis satu baris:

```dart
final res = await http.post(Uri.parse('$baseUrl/transfers'), headers: headers, body: jsonEncode(body));
```

Semua yang terjadi setelah `await` dulu tidak pernah ia lihat. Sekarang Raka yang menulisnya, dan ia harus menjawab tiga pertanyaan:

1. **Di mana aturan diperiksa?** App boleh memeriksa format nominal lebih dulu (langkah 1). Saldo cukup atau tidak hanya bisa diputuskan logika bisnis di server (langkah 4).
2. **Status apa untuk tiap kegagalan?** Token salah ditolak handler dengan `401` (langkah 3). Saldo kurang ditolak logika bisnis dengan `422` (langkah 4). Database yang tidak terjangkau berakhir sebagai `500` (langkah 5).
3. **Apa yang dikirim balik di response?** Response membawa saldo terbaru (langkah 8), jadi app langsung memperbarui layar tanpa request kedua (langkah 9).

Varian "sinyal putus" di widget juga bukan teori. PRD v1 sudah mencatat sinyal buruk di lantai dasar Gedung A sebagai risiko. Masalah ini kembali di Tahap 2 sebagai dobel bayar.

### Cara kerjanya

Satu request terdiri dari empat bagian. Satu response terdiri dari tiga. Contohnya diambil dari rekaman lab `labs/api-t1/output/bayar.txt`.

| Request | Contoh: bayar ke warung | Response | Contoh |
|---|---|---|---|
| Method | `POST` (membuat data baru) | Status | `201 Created` |
| Path | `/transfers` | Header | `Location: /transfers/1` |
| Header | `Authorization: Bearer ...` | Body | `{"id":1,"saldo":225000}` |
| Body | `{"ke": 418, "jumlah": 25000}` | | |

Di backend Rekeningo, bayar ke warung adalah transfer dari akun karyawan ke akun warung, jadi path-nya `/transfers`. Field `ke` berisi nomor akun Warung Ani (418), bukan namanya. Di dalam API, request melewati tiga lapisan, dan masing-masing boleh menghentikan perjalanan:

<Rantai data={lapisan} />

Ada satu kegagalan yang **tidak** menghasilkan status apa pun: response hilang di jalan. App hanya tahu "tidak ada jawaban". App tidak bisa membedakan "server gagal" dari "server sukses, tapi jawabannya hilang".

Tombol "Coba lagi" untuk aksi yang memindahkan uang baru aman bila server bisa mengenali request yang diulang. Caranya, idempotency key, ada di Tahap 2. Arti tiap status code didefinisikan di [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), dan ringkasannya ada di [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status).

### Di stack lain

Ketiga lapisan ada di semua stack, dengan nama berbeda.

| Stack | Handler | Logika bisnis | Akses data |
|---|---|---|---|
| Go (`net/http`) | `http.HandlerFunc` | struct service biasa | `database/sql` atau sqlc |
| Node.js (Express) | route handler `app.post(...)` | modul fungsi biasa | `pg` atau query builder |
| Laravel | Controller | class service atau action | Eloquent model atau query builder |
| Django | View | modul fungsi (sering `services.py`, konvensi tim) | ORM model |
| Dart (Serverpod) | class turunan `Endpoint`, method menerima `Session` | class Dart biasa | `Model.db` dari model hasil generator |
| Supabase | PostgREST (otomatis) | fungsi SQL atau Edge Function | tabel + RLS |

Framework menyediakan tempat untuk handler dan akses data. Lapisan logika bisnis biasanya harus kamu jaga sendiri, karena kode paling mudah ditulis langsung di handler. Itu topik [[t1-struktur-folder]] dan [[B7.1]].

### Trade-off: berapa lama app menunggu

Satu keputusan kecil yang langsung terasa di app: berapa lama app menunggu response sebelum menyerah?

| Timeout di app | Kelebihan | Kekurangan |
|---|---|---|
| Pendek (mis. 5 detik) | Budi cepat dapat kabar | Lebih sering "gagal" padahal server sukses |
| Panjang (mis. 30 detik) | Lebih jarang gagal palsu | Budi menatap loading lama, lalu menutup app |
| Mana pun, ditambah idempotency key | Aman diulang | Butuh kerja di app dan backend (Tahap 2) |

Angka 5 dan 30 detik di atas hanya contoh. Ukur waktu respons API-mu sendiri sebelum memilih.

Status untuk saldo kurang (`400`, `409`, atau `422`) adalah keputusan tersendiri. Raka memutuskannya di ADR 2, setelah masalah pertama muncul ([[B6]]).

</Blok>

### Cek diri

**1.** App mengirim `{"ke": "418", "jumlah": 25000}`: nomor akun sebagai teks, bukan angka. Lapisan mana yang menolak, dan status apa yang diterima app?

<details class="success">
<summary>Jawaban</summary>

Handler yang menolaknya, karena ini soal format data: server mengharapkan angka. App menerima status `400 Bad Request` dengan `tipe-salah` untuk field `ke` (rekaman lab `labs/api-t1/output/m2.txt` bagian E). Logika bisnis tidak dijalankan sama sekali, jadi saldo Budi tidak berubah.

</details>

**2.** Response pembayaran membawa `saldo` terbaru. Apa gunanya bagi app?

<details class="success">
<summary>Jawaban</summary>

App bisa langsung memperbarui layar tanpa request `GET` kedua. Satu perjalanan lebih sedikit berarti lebih cepat dan lebih sedikit tempat yang bisa gagal.

</details>

**3.** Jelaskan kenapa app tidak boleh otomatis mengulang `POST /transfers` setelah timeout.

<details class="success">
<summary>Jawaban</summary>

Timeout tidak berarti gagal. Database mungkin sudah COMMIT, dan hanya response yang hilang. Mengulang request berarti meminta pembayaran kedua. Tanpa idempotency key, backend akan memprosesnya, dan Budi membayar dua kali.

</details>

### Saat me-review kode AI, cek ini

- [ ] Handler hanya mengurus HTTP: parsing, token, format. Aturan bisnis ada di lapisan lain.
- [ ] Setiap jalur gagal mengembalikan status yang tepat, bukan `200` dengan `{"error": ...}`.
- [ ] Response aksi tulis membawa data yang dibutuhkan app untuk memperbarui layar.
- [ ] Di app: `POST` yang memindahkan uang tidak di-retry otomatis tanpa idempotency key.
- [ ] Ada timeout eksplisit di client HTTP app, bukan bawaan tanpa batas.
