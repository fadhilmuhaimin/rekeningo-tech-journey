## Inti

Secret adalah nilai yang membuka sesuatu: password database, token registry, kunci SSH. Repo hanya tahu nama secret. Nilainya hanya ada di mesin yang memakainya.

<Rantai data={tempat} ringkas />

Di [[t1-m7]] password `rekeningo_app` ikut di setiap clone sejak minggu 1. ADR 11 mencegah kejadian berikutnya: `.env.example` tanpa nilai, gitleaks di laptop dan di CI, dan nilai asli hanya di `.env` VPS.

### Apa saja secret di Rekeningo v1

| Secret | Dipakai oleh | Tempatnya menurut ADR 11 |
|---|---|---|
| Password role `rekeningo_app` | Container API, lewat `DATABASE_URL` | `.env` di VPS, di folder yang sama dengan `compose.yaml` |
| Token GHCR dengan izin `read:packages` | `docker login ghcr.io` di VPS | File konfigurasi Docker di VPS |
| Password database lokal | Raka saat develop | `.env` di laptop, berbeda dari password VPS |
| `GITHUB_TOKEN` | Workflow CI | Dibuat GitHub di awal setiap job, berakhir saat job selesai |
| Kunci SSH untuk CI ke VPS | Belum ada | Tidak dibuat di Tahap 1; deploy tetap manual ([[C3]]) |

Dari luar GitHub Actions, seperti dari VPS, GHCR hanya menerima personal access token (classic), dan izin `read:packages` dipakai untuk mengunduh image ([docs.github.com](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)). Tanpa credential store, `docker login` menyimpan token itu di `~/.docker/config.json` dalam bentuk base64 ([docs.docker.com](https://docs.docker.com/reference/cli/docker/login/)). Base64 bukan enkripsi, jadi file itu dijaga sama seperti `.env`.

`GITHUB_TOKEN` dibuat untuk setiap job dan berakhir saat job selesai ([docs.github.com](https://docs.github.com/en/actions/concepts/security/github_token)). Karena deploy masih manual, repo Rekeningo tidak menyimpan secret jangka panjang di CI.

### Dari mana Compose mengambil `DATABASE_URL`

`compose.yaml` dari [[C3]] hanya menyebut nama variabelnya:

<Snippet file="labs/api-t1/deploy/compose.yaml" lines="9:10" lang="yaml" title="labs/api-t1/deploy/compose.yaml" />

Compose mengisi `${DATABASE_URL}` dari environment shell lebih dulu. Kalau tidak ada, Compose membaca file `.env` di folder proyek, biasanya folder tempat `compose.yaml` berada ([docs.docker.com](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)). Di VPS nilainya ada di `.env` itu, dengan `chmod 600` supaya hanya user deploy yang bisa membacanya. Lab mengisinya lewat environment shell, jadi `.env` VPS tidak direkam.

### Kenapa aturan bawaan gitleaks belum menangkap semuanya

Aturan bawaan v8.30.1 menandai `POSTGRES_PASSWORD`, tapi tidak menandai password yang sama di dalam `DATABASE_URL` ([[t1-m7]]). Aturan tambahan di `.gitleaks.toml` menutup celah itu. `useDefault = true` mempertahankan aturan bawaan, `secretGroup = 1` menunjuk grup regex yang dihitung sebagai secret, dan `keywords` menyaring isi sebelum regex diperiksa ([gitleaks v8.30.1](https://github.com/gitleaks/gitleaks/blob/v8.30.1/README.md)).

<Snippet files={["labs/api-t1/output/m7.txt:68:78","labs/api-t1/output/m7.txt:93:103"]} title="Rekaman lab: labs/api-t1/output/m7.txt, bagian E" />

Aturan apa pun hanya mengenali pola yang sudah ditulis. Secret dengan format baru lolos sampai aturannya ada. Karena itu gitleaks adalah pagar, bukan bukti bahwa repo bersih.

### Riwayat lama di CI: `.gitleaksignore`

Langkah CI memindai seluruh riwayat di setiap push. Commit minggu 1 akan selalu ditandai, walau password-nya sudah diganti. File `.gitleaksignore` di root repo mencatat temuan yang sengaja dilewati menurut fingerprint-nya ([gitleaks v8.30.1](https://github.com/gitleaks/gitleaks/blob/v8.30.1/README.md)).

<Snippet file="labs/api-t1/output/m7.txt" lines="221:250" title="Rekaman lab: labs/api-t1/output/m7.txt, latihan bagian J" />

Fingerprint memuat hash commit, nama file, aturan, dan nomor baris. Temuan di commit lain tetap menggagalkan pemindaian, seperti `catatan-vps.env` dari latihan bagian H. Fingerprint hanya dicatat sesudah password-nya diganti.

### Mengganti password tanpa sesi lama tertinggal

<Rantai data={rotasi} />

Urutan di VPS:

1. Ganti password dengan `\password rekeningo_app` di psql. `ALTER ROLE ... PASSWORD` mengirim password sebagai teks biasa, yang bisa tercatat di riwayat perintah atau log server ([postgresql.org](https://www.postgresql.org/docs/17/sql-alterrole.html)).
2. Tulis password baru di `.env` VPS.
3. Jalankan `TAG=<hash yang sedang jalan> docker compose up -d`. Konfigurasi container berubah, jadi Compose menghentikan container lama dan membuat yang baru ([docs.docker.com](https://docs.docker.com/reference/cli/docker/compose/up/)).
4. Putus sesi role `rekeningo_app` yang dibuka sebelum langkah 1 dengan `pg_terminate_backend`.

Di antara langkah 1 dan 3, container lama masih membawa `DATABASE_URL` lama. Lab memerankannya dengan sesi A, yang dibuka sebelum password diganti. Lab memakai `ALTER ROLE` dengan password palsu yang dibangkitkan saat lab berjalan:

<Snippet file="labs/api-t1/output/m7.txt" lines="198:219" title="Rekaman lab: labs/api-t1/output/m7.txt, latihan bagian I" />

Sesi A tetap jalan sesudah `ALTER ROLE`, sedangkan koneksi baru dengan password lama ditolak. Jadi koneksi yang sudah ada di pool container lama tetap melayani, tapi setiap koneksi baru gagal sampai langkah 3. Lab tidak mengukur lamanya jeda itu.

Langkah 4 menutup sesi siapa pun yang sudah masuk dengan password lama. Dengan `timeout`, `pg_terminate_backend` menunggu sampai prosesnya benar-benar berhenti ([postgresql.org](https://www.postgresql.org/docs/17/functions-admin.html)). Tanpa langkah 4, orang yang membaca password dari riwayat dan sudah terhubung tetap memegang sesinya.

Bagi app Flutter, aturan ini sudah berlaku sejak [[A4]]: app tidak pernah memegang password database. App hanya memegang token sesi user-nya sendiri, di secure storage ([[t1-idor]]).

### ADR 11: nama secret di repo, nilainya hanya di server

**Kebutuhan.** Di M7, password database VPS ada di setiap clone dari minggu 1 sampai minggu 5. Secret v1 ada dua: password `rekeningo_app` dan token GHCR. Engineer-nya satu, laptopnya satu, VPS-nya satu. Secret tidak boleh masuk riwayat lagi, yang lolos harus ketahuan di CI, dan password harus bisa diganti tanpa mengubah kode.

| Opsi | Kelebihan | Kekurangan |
|---|---|---|
| `.env` di repo privat (minggu 1–5) | Laptop baru langsung jalan | Setiap clone dan fork memegang password; riwayat tidak lupa ([[t1-m7]]) |
| **`.env.example` tanpa nilai, gitleaks di hook dan CI, nilai asli hanya di `.env` VPS** | Tanpa layanan baru; repo hanya tahu nama variabel | Hook bisa dilewati dan tidak ikut di-clone; rotasi manual dengan jeda |
| File secret terenkripsi di repo, misalnya [SOPS](https://github.com/getsops/sops) | Nilai ikut versi kode; perubahan secret tercatat | Kunci dekripsi menjadi secret baru di luar repo; ciphertext lama tetap di riwayat, jadi kunci yang bocor membuka semua versi |
| Secret manager | Akses per mesin tercatat; rotasi otomatis | Layanan baru, identitas mesin, dan biaya untuk dua secret di satu VPS |
| Secret di GitHub Actions, CI menulis `.env` ke VPS | Nilai tidak ada di laptop | CI butuh kunci SSH ke VPS, secret jangka panjang baru; deploy otomatis belum ada ([[C3]]) |

**Yang dipilih.** Opsi kedua. Wujudnya di repo Rekeningo:

1. `.env` ada di `.gitignore`. `.env.example` hanya berisi nama variabel (rekaman bagian G).
2. Hook pre-commit gitleaks di laptop memakai entry resmi `gitleaks git --pre-commit --staged` (bagian G). Laptop baru memasangnya sendiri, karena hook tidak ikut di-clone.
3. Aturan `url-dengan-password` di `.gitleaks.toml`, dengan aturan bawaan tetap aktif (bagian E).
4. CI memindai seluruh riwayat di setiap push ke `main`. Dua temuan minggu 1 dicatat di `.gitleaksignore` (bagian J).
5. Nilai asli hanya di VPS: `.env` di folder Compose dengan `chmod 600`, dan token GHCR di file konfigurasi Docker. Password VPS yang di [[t1-m7]] masih tersalin ke `.env` laptop dihapus dari sana, dan laptop memakai database lokal.
6. CI tidak memegang kunci ke VPS. Token CI hanya `GITHUB_TOKEN` per job.
7. Saat secret bocor: ganti dulu dengan empat langkah di blok Paham, baru catat fingerprint-nya.

Langkah CI-nya ditambahkan ke `ci.yml` dari [[C3]]:

<Snippet file="labs/api-t1/deploy/ci.yml" lines="15:25" lang="yaml" title="labs/api-t1/deploy/ci.yml" />

`fetch-depth: 0` membuat checkout memuat seluruh riwayat, sehingga commit lama ikut dipindai. `.gitleaks.toml` dan `.gitleaksignore` dibaca dari root repo, sama seperti di rekaman bagian E dan J.

**Coba keduanya.** Opsi pertama direkam di [[t1-m7]]: `git show 80952b1:.env` mencetak password dari riwayat. Opsi kedua direkam di blok Coba: hook menolak `.env.example` berisi password, dan pemindaian menangkap commit yang melewati hook.

**Pre-mortem.** Enam bulan lagi, password bocor lagi. Tiga penyebab yang paling mungkin:

1. Laptop baru tanpa hook. Pagarnya: langkah gitleaks di CI, yang tidak bergantung pada laptop.
2. Secret dengan format yang tidak dikenal aturan, seperti `DATABASE_URL` sebelum bagian E. Pagarnya: setiap jenis secret baru diuji dengan nilai palsu, lalu aturannya ditambah bila lolos.
3. `.gitleaksignore` dipakai untuk membungkam temuan yang belum dirotasi. Pagarnya: fingerprint hanya ditambah sesudah rotasi selesai, dan setiap baris baru di file itu dibaca saat review.

**Kapan keputusan ini salah.** Saat orang atau mesin kedua butuh secret yang sama, menyalin `.env` lewat chat tidak tercatat dan tidak bisa dicabut per orang. Saat CI harus men-deploy sendiri, CI butuh kunci ke VPS. Saat layanan melayani publik 24 jam, jeda di antara langkah 1 dan 3 tidak bisa lagi ditaruh di luar jam ramai. Saat VPS sendiri dibobol, `.env` ikut terbaca, karena ADR ini hanya menjaga repo.

**Yang merevisinya nanti.** Tahap 2 tetap memakai aturan ini: `.env` tidak pernah di repo, dan gitleaks sudah ada. Tahap 3 menambah staging otomatis dari CI, jadi tempat kunci deploy diputuskan di sana. Tahap 4 memindahkan secret ke secret manager, bersama cloud managed dan tiga tim.

### Sengaja belum dilakukan

| Yang ditunda | Kenapa ditunda | Muncul lagi di |
|---|---|---|
| Secret manager | Dua secret, satu VPS, satu engineer | Tahap 4 |
| Menulis ulang riwayat dengan git-filter-repo | Password lama sudah tidak membuka apa pun; commit lama tetap ada di clone yang sudah memuatnya ([[t1-m7]]) | Tidak direncanakan |
| CI men-deploy ke VPS | Butuh kunci SSH di CI | Tahap 3, bersama staging |
| Rotasi tanpa jeda | Puncak 0,14 request per detik (angka cerita); rotasi dijalankan di luar jam makan siang | Tahap 4 |

### Cek diri

**1.** Raka memakai laptop baru, meng-clone repo, lalu langsung bekerja. Seminggu kemudian ia meng-commit file berisi token GHCR. Apa yang terjadi?

<details class="success">
<summary>Jawaban</summary>

Commit diterima, karena hook tidak ikut di-clone. Kalau aturan gitleaks mengenali format token itu, langkah CI menandainya sesudah push. Saat itu token sudah ada di remote, jadi token harus dicabut dan diganti.

</details>

**2.** Raka mengganti password, mengisi `.env` VPS, menjalankan `docker compose up -d`, lalu berhenti. Seseorang sudah membuka psql dengan password dari riwayat sejak pagi. Apakah sesinya masih jalan?

<details class="success">
<summary>Jawaban</summary>

Masih. Rekaman bagian I menunjukkan `ALTER ROLE` tidak memutus sesi yang sudah terbuka. Sesi itu baru berhenti di langkah 4, `pg_terminate_backend` untuk sesi yang dibuka sebelum rotasi.

</details>

**3.** CI gagal karena temuan di commit minggu 1. Sebelum mengganti password, Raka menambah fingerprint-nya ke `.gitleaksignore` supaya CI hijau. Apa masalahnya?

<details class="success">
<summary>Jawaban</summary>

CI hijau, tapi password di riwayat masih membuka database. `.gitleaksignore` hanya membuat gitleaks diam, dan password tidak berubah. Urutannya: ganti password, lalu catat fingerprint.

</details>

### Saat me-review kode AI, cek ini

- File baru bernama `.env` atau `*.env`, atau baris `PASSWORD=` dan `TOKEN=` yang berisi nilai.
- Connection string dengan `user:password@` di kode, tes, atau README.
- Nilai cadangan untuk secret di kode, misalnya string tetap saat `DATABASE_URL` kosong.
- Baris baru di `.gitleaksignore` tanpa catatan rotasi.
- Log yang mencetak seluruh environment atau config.
