## Inti

Method menyatakan maksud request, status code menyatakan hasilnya, dan header membawa informasi tambahan.

<Rantai data={tigaBagian} ringkas />

Budi membayar lewat `POST /transfers`. Server menjawab `201 Created` dengan header `Location: /transfers/1`, jadi app bisa membuka transaksi itu tanpa menyusun alamatnya sendiri. Kalau alamat yang sama dibuka tanpa token, server menjawab `401` dan header `WWW-Authenticate` yang menyebut skema autentikasi yang diterima.

Dari ketiganya, app memutuskan apa yang ditampilkan tanpa menebak isi body: `201` berarti pembayaran tercatat, `401` berarti Budi harus login lagi. Method juga menentukan boleh tidaknya request diulang. `GET` aman diulang, sedangkan `POST /transfers` yang diulang bisa membuat pembayaran kedua.

### Kenapa ini ada

Di [[t1-m1]], input yang sama menghasilkan tiga status berbeda tergantung versi server: `201`, `500`, dan `422`. Di app absensi lama, Raka terbiasa menulis `if (res.statusCode == 200)`. Kode itu membaca `201` sebagai gagal, dan tidak bisa membedakan "nominalmu salah" dari "server rusak".

### Cara kerjanya

**Method** menyatakan maksud. Dua sifatnya penting untuk app, karena menentukan boleh tidaknya request diulang ([RFC 9110 §9.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-common-method-properties)):

| Method | Untuk | Safe (tidak mengubah data) | Idempotent (aman diulang) |
|---|---|---|---|
| `GET` | Membaca: `GET /akun/419` | Ya | Ya |
| `POST` | Membuat atau memproses: `POST /transfers` | Tidak | Tidak |
| `PUT` | Mengganti seluruh resource | Tidak | Ya |
| `PATCH` | Mengubah sebagian resource ([RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)) | Tidak | Tidak (RFC 5789) |
| `DELETE` | Menghapus | Tidak | Ya |

**Status code** dikelompokkan oleh digit pertamanya: `2xx` berhasil, `4xx` kesalahan di sisi pengirim, `5xx` kesalahan di sisi server ([RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes)). Bedakan dua yang sering tertukar:

- `401 Unauthorized`: server belum tahu siapa kamu. Token tidak ada, salah, atau kedaluwarsa.
- `403 Forbidden`: server tahu siapa kamu, tapi kamu tidak boleh melakukannya. Rekeningo menjawab `404` untuk data milik orang lain; alasannya di [[B5.3]].

**Header** membawa informasi di luar body. Yang muncul di rekaman lab:

| Header | Arah | Isinya |
|---|---|---|
| `Authorization: Bearer <token>` | request | Token sesi |
| `Content-Type` | keduanya | Format body, misalnya `application/json`, atau `application/problem+json` untuk error |
| `Location: /transfers/1` | response `201` | Alamat resource yang baru dibuat |
| `WWW-Authenticate` | response `401` | Cara autentikasi yang diterima. Wajib menyertai `401` ([RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#status.401)) |
| `Allow` | response `405` | Method yang diterima path ini |

Tiga detail dari rekaman di atas:

- `405` dari router bawaan Go berupa teks biasa, bukan problem+json. Kalau app mengharapkan semua error berformat JSON, router perlu dikonfigurasi. Format error dibahas di [[B6]].
- Go menulis nama header `Www-Authenticate`. Nama header tidak peka huruf besar-kecil ([RFC 9110 §5.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-field-names)), jadi app harus membacanya tanpa membedakan huruf.
- Go menulis `422 Unprocessable Entity`, nama lama sebelum RFC 9110 menggantinya jadi "Unprocessable Content". App wajib mengabaikan teks itu dan hanya membaca angkanya ([RFC 9112 §4](https://www.rfc-editor.org/rfc/rfc9112.html#name-status-line)).

### Trade-off: kapan pakai apa

| Pilihan | Kelebihan | Kekurangan |
|---|---|---|
| Selalu `200`, status di body | Satu jalur parsing di app | App, proxy, log, dan monitoring tidak bisa membedakan sukses dari gagal |
| Status code yang tepat | App, log, dan metric error bekerja tanpa membaca body | Tim harus sepakat status mana untuk kasus mana |
| Status yang tepat + body error standar ([[B6]]) | App bisa menampilkan pesan yang spesifik | Sedikit lebih banyak kode di server |

Rekeningo v1 memakai baris ketiga. Keputusan ini salah kalau Rekeningo harus melayani client yang hanya mengerti `200`, misalnya integrasi lama; itu belum ada di v1.

### Sengaja belum dilakukan

| Yang ditunda | Kenapa ditunda | Muncul lagi di |
|---|---|---|
| `405` berformat problem+json | Hanya terjadi kalau app salah method; app v1 dibuat Raka sendiri | Saat ada client pihak ketiga |
| Mengulang `POST /transfers` dengan aman | `POST` tidak idempotent; v1 menunda retry dari app | Tahap 2: [[E3]] |
| Daftar halaman di riwayat | Riwayat v1 dibatasi 20 baris | Tahap 2: [[B1.3]] |

### Cek diri

**1.** Budi membuka `GET /akun/419` dengan token yang sudah kedaluwarsa. Status apa yang tepat: `401` atau `403`?

<details class="success">
<summary>Jawaban</summary>

`401`. Token kedaluwarsa berarti server tidak bisa memastikan siapa pengirimnya. `403` dipakai kalau server tahu siapa kamu, tapi aksinya tidak diizinkan.

</details>

**2.** Jelaskan kenapa app tidak boleh bergantung pada teks "Unprocessable Entity" di status line.

<details class="success">
<summary>Jawaban</summary>

RFC 9112 menyatakan client harus mengabaikan teks itu, karena bisa berbeda antar server atau hilang di HTTP/2. Buktinya ada di lab: Go menulis "Unprocessable Entity", padahal RFC 9110 menamainya "Unprocessable Content". Yang bisa diandalkan hanya angka `422`.

</details>

**3.** Response `201` membawa header `Location: /transfers/1`. Apa gunanya bagi app?

<details class="success">
<summary>Jawaban</summary>

App tahu alamat pembayaran yang baru dibuat, dan bisa membukanya lagi untuk layar bukti bayar tanpa menyusun URL sendiri. Rekaman lab menunjukkan `GET /transfers/1` menjawab `200` dengan jumlah Rp25.000.

</details>

### Saat me-review kode AI, cek ini

- [ ] Tidak ada `200` untuk kegagalan, dan tidak ada `{"success": false}` dengan status `200`.
- [ ] `POST` yang membuat resource menjawab `201` dengan header `Location` yang benar-benar bisa dibuka.
- [ ] `401` hanya untuk "belum dikenali"; data milik orang lain dijawab `404` atau `403` sesuai kesepakatan.
- [ ] `GET` tidak mengubah data, karena bisa diulang oleh app, proxy, atau browser.
- [ ] App membaca angka status dan `Content-Type`, bukan teks status line.
