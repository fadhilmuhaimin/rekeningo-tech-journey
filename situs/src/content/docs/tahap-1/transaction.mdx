## Inti

Transaction menjadikan beberapa perintah database satu unit: berhasil semua, atau batal semua.

<Rantai data={commitRollback} ringkas />

Setelah `begin`, setiap perintah mengubah data, tapi perubahannya belum permanen. Pembayaran Rp25.000 menjalankan dua `UPDATE` dan satu `INSERT`, lalu `commit` menyimpan ketiganya sekaligus. App menerima `201`, saldo Budi Rp225.000, dan saldo Ani Rp25.000.

Pembayaran Rp70.000 di versi benar M4 berhenti di `UPDATE` kedua karena batas saldo warung. Server mengirim `rollback`, dan `UPDATE` pertama ikut batal. Saldo Budi tetap Rp250.000, dan total saldo tetap Rp25.000.000.

2. Di Go, kenapa `defer tx.Rollback()` aman walau `tx.Commit()` sudah berhasil?
3. Di Laravel atau Django, siapa yang mengirim `ROLLBACK` saat ada error?

    await Akun.db.updateRow(session, budi, transaction: transaction);

<Blok nama="Paham">

### Kenapa ini ada

Di [[t1-m4]], server menjalankan tiga perubahan uang sebagai tiga perintah terpisah. Perintah kedua ditolak, perintah pertama sudah tersimpan. Saldo Budi turun Rp70.000, saldo Ani tetap, dan jumlah semua saldo tidak lagi sama dengan jumlah top-up.

Batas saldo warung hanya salah satu penyebab. Koneksi putus, server di-restart saat deploy, atau constraint lain meninggalkan keadaan yang sama. Transaction melindungi dari semuanya, karena ia tidak peduli kenapa satu langkah gagal.

Kalau kamu pernah memakai `database.transaction((txn) async { ... })` di [sqflite](https://pub.dev/packages/sqflite), konsepnya sama persis. Bedanya, di backend banyak user menulis ke database yang sama pada waktu bersamaan. Itu masalah Tahap 2, di [[B3.2]].

### Cara kerjanya

- **`BEGIN`** membuka transaction. Di PostgreSQL, perubahan sesudahnya belum terlihat oleh koneksi lain sampai `COMMIT`.
- **`COMMIT`** membuat semua perubahan permanen sekaligus.
- **`ROLLBACK`** membatalkan semua perubahan sejak `BEGIN`.

Sifat "semua atau tidak sama sekali" ini disebut **atomicity**, huruf A di ACID. Dokumentasi PostgreSQL mendefinisikannya begini: dari sudut pandang transaction lain, sebuah transaction terjadi seluruhnya atau tidak sama sekali ([PostgreSQL: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html)).

Satu hal yang sering terlewat: database tidak menutup transaction sendiri saat satu perintah gagal. Aplikasi yang harus mengakhirinya. Di rekaman M4 versi benar, `rollback` dikirim oleh `defer tx.Rollback()` di kode Go, bukan oleh PostgreSQL:

<Blok nama="Putuskan">

### Trade-off: kapan pakai apa

| Situasi | Pilihan |
|---|---|
| Beberapa perubahan harus konsisten, misalnya dua saldo dan satu baris transaksi | Satu transaction |
| Hanya satu perintah SQL | Tidak perlu `BEGIN`; PostgreSQL membungkusnya sendiri |
| Perlu memanggil API luar, misalnya payment gateway atau kirim email | Jangan di dalam transaction. API luar tidak ikut di-rollback, dan koneksi database tertahan selama menunggu |
| Data tersebar di dua database atau dua service | Transaction biasa tidak menjangkau keduanya. Butuh pola lain (outbox, saga), dibahas di [[B10.2]] dan [[D3]] |

**Biaya transaction.** Selama terbuka, transaction memegang satu koneksi dari pool ([[B2.5]]). Baris yang diubahnya juga terkena lock, jadi transaction lain yang mengubah baris yang sama harus menunggu. Lock dibahas di [[B3.2]].

### Cek diri

**1.** Kode Go ini memakai `db.ExecContext` (bukan `tx.ExecContext`) untuk `UPDATE` pertama. `UPDATE` kedua lewat `tx` dan gagal. Dengan angka lab `b3-stack`, berapa jumlah kedua saldo sesudahnya?

```go
tx, _ := db.BeginTx(ctx, nil)
defer tx.Rollback()
db.ExecContext(ctx, `UPDATE akun SET saldo = saldo - 70000 WHERE nama = 'budi'`)
_, err := tx.ExecContext(ctx, `UPDATE akun SET saldo = saldo + 70000 WHERE nama = 'ani'`)
```

<details class="success">
<summary>Jawaban</summary>

Rp1.010.000, berkurang Rp70.000 seperti di M4. `db.ExecContext` berjalan di luar transaction, jadi langsung permanen. `tx.Rollback()` hanya membatalkan perintah yang lewat `tx`. Dokumentasi Go memperingatkan hal ini: jangan memanggil method `sql.DB` di dalam transaction ([Go](https://go.dev/doc/database/execute-transactions)).

</details>

**2.** Di Django, kamu menangkap `IntegrityError` **di dalam** blok `atomic()`, lalu menjalankan query lain di blok yang sama. Apa risikonya?

<details class="success">
<summary>Jawaban</summary>

Setelah error database, transaction sudah dalam keadaan rusak. Query berikutnya bisa gagal dengan `TransactionManagementError`. Dokumentasi Django menyarankan membungkus bagian yang boleh gagal dengan `atomic()` sendiri, lalu menangkap error di luar blok itu ([Django](https://docs.djangoproject.com/en/stable/topics/db/transactions/)).

</details>

**3.** Jelaskan dalam satu kalimat: kenapa memanggil API payment gateway di dalam transaction itu ide buruk?

<details class="success">
<summary>Jawaban</summary>

Kalau transaction di-rollback, uang di payment gateway sudah terlanjur ditarik, karena API luar tidak ikut rollback. Selain itu, koneksi dan lock tertahan selama menunggu respons yang bisa lambat.

</details>

### Saat me-review kode AI, cek ini

- [ ] Semua perintah dalam satu unit kerja memakai objek transaction yang sama (`tx`, `client`, `DB::transaction`, parameter `transaction`), bukan koneksi atau pool global.
- [ ] Ada jalur `ROLLBACK` yang pasti jalan saat error: `defer tx.Rollback()`, `catch` + `ROLLBACK`, atau closure framework.
- [ ] Error di dalam transaction tidak ditangkap lalu diabaikan.
- [ ] Tidak ada panggilan HTTP atau API luar di dalam transaction.
- [ ] Nominal uang disimpan sebagai integer rupiah (`bigint`) atau `numeric`, bukan `float`.
