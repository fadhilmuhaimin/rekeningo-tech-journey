## Inti

Setiap lapisan hanya tahu satu hal: handler tahu HTTP, service tahu aturan uang, repo tahu SQL.

<Rantai data={lapisanArah} ringkas />

Arah ini dibaca dari daftar import tiap folder. Handler hanya mengimpor `service`, service hanya mengimpor `repo`, dan hanya repo yang mengimpor `database/sql`. Jadi input dari app hanya bisa menjadi SQL di satu folder, dan review injection cukup membaca folder itu.

Compiler Go tidak memeriksa arah ini. Handler buatan AI yang menjalankan `SELECT` sendiri tetap lolos `go build`. Skrip `cek_arah.py` membaca import yang sama dan menolaknya dengan exit 1, sehingga aturan arah diperiksa mesin, bukan diingat.

### Kenapa ini ada

Setelah [[t1-m3]], Raka bertanya: di mana saja input dari app bisa berubah menjadi SQL? Kalau jawabannya "di mana saja", setiap review harus membaca setiap file. Kalau jawabannya "hanya di `repo/`", review injection dan gosec hanya perlu melihat satu folder.

Kesalahan kedua M3 juga melewati lapisan. Repo mengembalikan struct `Akun` lengkap dengan saldo, service meneruskannya, dan handler mengirimnya apa adanya ke app. Di [[t1-struktur-folder]], Raka menulis aturan arah sebagai rencana. Setelah M3, aturan itu perlu diperiksa, bukan hanya ditulis.

### Cara kerjanya

| Lapisan | Tahu tentang | Tidak boleh tahu | Folder lab |
|---|---|---|---|
| Handler | HTTP: path, query, JSON, sesi, status code | SQL, tabel | `internal/handler` |
| Service | Aturan uang: batas bayar, saldo cukup, hanya ke warung | HTTP, JSON, SQL | `internal/service` |
| Repo | SQL, transaction, nama tabel | HTTP, aturan uang | `internal/repo` |

Handler membaca `cari` dari URL dan menulis JSON. Ia tidak pernah melihat teks SQL. Service di Tahap 1 masih tipis untuk pencarian, karena belum ada aturan uang di sana. Repo memegang satu-satunya query, dengan parameter `$1` dari ADR 4.

**Arah import, menurut mesin.** Di Go, sebuah paket hanya bisa menyebut paket lain yang ia impor. Daftar import setiap lapisan bisa dibaca dengan `go list`:

**Ubah satu hal: pintas buatan AI.** Lab menambah file sementara: handler yang menjalankan query pencarian sendiri. Query-nya bahkan memakai `$1`, jadi aman dari injection. Masalahnya ada di tempatnya:

Compiler menerima kode itu. Pemeriksa arah menolaknya, karena sekarang ada dua folder yang bisa menyusun SQL dari input. Pintas seperti ini sering muncul saat AI diminta "tambahkan endpoint secepatnya".

**Yang tidak tertangkap daftar import.** Handler tidak mengimpor `repo`, tapi tetap menerima nilai bertipe `repo.WarungRingkas` dari service. Go mengizinkannya selama nama paketnya tidak ditulis. Akibatnya, tag JSON di struct milik repo menentukan apa yang sampai ke app:

Di M3, struct inilah yang membawa saldo ke layar Dimas. Di Tahap 1, Raka memilih jalan sederhana dari ADR 4: repo punya struct khusus per layar, seperti `WarungRingkas`. Pemisahan tipe antar lapisan baru dibutuhkan saat tim bertambah.

**Kapan berlebihan.** Untuk satu orang, lapisan berikut biasanya menambah file tanpa menjawab masalah:

- Interface untuk setiap struct, padahal implementasinya hanya satu dan tidak pernah diganti di tes.
- DTO, entity, dan model terpisah untuk data yang bentuknya sama.
- Framework dependency injection, padahal `main.go` menyusun tiga objek.

### Di stack lain

Pemisahan lapisannya sama; yang berbeda adalah alat pemeriksa arahnya.

| Stack | Alat pemeriksa arah | Sumber |
|---|---|---|
| Go | depguard: daftar paket yang dilarang per kelompok file; bisa dijalankan lewat golangci-lint | [depguard](https://github.com/OpenPeeDeeP/depguard) |
| Express, NestJS | eslint-plugin-boundaries: aturan siapa boleh bergantung pada siapa | [eslint-plugin-boundaries](https://github.com/javierbrea/eslint-plugin-boundaries) |
| Laravel | Deptrac: analisis statis yang memeriksa ketergantungan antar lapisan | [Deptrac](https://deptrac.github.io/deptrac/) |
| Django | import-linter, contract `layers`: lapisan atas boleh mengimpor bawah, tidak sebaliknya | [import-linter: layers](https://import-linter.readthedocs.io/en/latest/contract_types/layers/) |

Lab memakai skrip pendek karena aturannya hanya tiga baris. Logikanya sama dengan depguard: baca daftar import, bandingkan dengan larangan.

### Trade-off: berapa lapisan untuk satu orang

| Pilihan | Kelebihan | Kekurangan |
|---|---|---|
| Semua di handler | Tercepat ditulis, satu file | SQL dan aturan uang tersebar; review injection harus membaca semua file |
| **Tiga lapisan, arah diperiksa mesin** | SQL di satu folder; aturan uang di satu folder; pelanggaran tertangkap sebelum review | Satu fitur tersebar di tiga folder; pemeriksa harus dijalankan |
| Banyak lapisan: port dan adapter, DI, DTO per lapisan | Berguna untuk tim besar dengan banyak sumber data | Lebih banyak kode perantara daripada fitur untuk satu orang |

**Kapan pilihan ini salah.** Saat tiga tim bekerja di satu codebase, satu folder `service/` berisi aturan semua tim dan mulai bentrok. Di Tahap 4, lapisan dipecah lagi per modul ([[B7.2]]).

### Sengaja belum dilakukan

| Yang ditunda | Kenapa ditunda | Muncul lagi di |
|---|---|---|
| Interface untuk repo, supaya service bisa dites tanpa database | Belum ada tes otomatis sama sekali | [[C1]] |
| Pemeriksa arah di CI | CI belum ada; skrip dijalankan sebelum commit | [[t1-tim-infra]] |
| Tipe response terpisah dari struct repo | Satu orang, delapan operasi; struct per layar dari ADR 4 menutup kebocoran M3 | Tahap 4 |

<Blok nama="Kunci">

### Cek diri

**1.** Raka menambah fitur: admin menjalankan bayar dari skrip CSV, tanpa HTTP. Lapisan mana yang dipakai skrip itu?

<details class="success">
<summary>Jawaban</summary>

Service dan repo. Skrip tidak menerima request, jadi handler tidak terlibat. Karena batas bayar dan cek saldo ada di service, keduanya otomatis berlaku untuk skrip.

</details>

**2.** `go build` lolos, tapi `cek_arah.py` gagal dengan "handler: mengimpor database/sql". Apa artinya, dan apa perbaikannya?

<details class="success">
<summary>Jawaban</summary>

Ada handler yang menjalankan SQL sendiri. Kodenya sah bagi Go, tapi melanggar aturan arah. Pindahkan query ke repo, tambahkan fungsi service yang memanggilnya, lalu handler memanggil service.

</details>

**3.** Kenapa saldo bisa sampai ke app di M3 walaupun handler tidak mengimpor repo?

<details class="success">
<summary>Jawaban</summary>

Handler menerima struct `repo.Akun` dari service dan mengirimnya apa adanya. Tag JSON di struct milik repo, termasuk `saldo`, ikut sampai ke app. Daftar import tidak menangkap tipe yang lewat, hanya paket yang diimpor.

</details>

### Saat me-review kode AI, cek ini

- [ ] Handler tidak berisi SQL, tidak mengimpor `database/sql`, dan tidak memutuskan aturan uang.
- [ ] Service tidak membaca request, header, atau menulis status code.
- [ ] Response tidak mengirim struct tabel apa adanya; field-nya hanya yang dibutuhkan layar.
- [ ] Pemeriksa arah dijalankan dan lolos.
- [ ] Setiap interface baru punya alasan: implementasi kedua, atau dipakai di tes.
