## Inti

Retry itu benar; yang salah adalah server yang tidak mengenali ulangan. App mengenalkannya dengan satu key per niat bayar.

<Rantai data={intiDiagram} ringkas />

Di [[t2-m10]], response pembayaran Budi hilang sesudah `COMMIT`, dan app mengulang request yang sama. Server minggu 2 menulis jurnal kedua (rekaman lab `tanpa-key.txt`). Retry-nya tidak salah, karena koneksi putus tidak memberi tahu app apa yang terjadi di server.

**Idempotency key** adalah penanda yang dibuat app dan dikirim di header `Idempotency-Key`, supaya server mengenali ulangan dari satu niat bayar. Penanda itu hanya berguna bila retry membawa key yang sama.

Key yang dibuat ulang di setiap percobaan tetap menghasilkan dua jurnal dan saldo Rp50.000 (rekaman `key-per-percobaan.txt`). Dengan satu key per niat, percobaan kedua menerima jawaban pertama dan saldo Budi Rp75.000 (rekaman `key-per-niat.txt`). ADR 14 di blok Putuskan memilih cara kedua.

### Kenapa ini ada

Raka mengira header dan tabel key sudah menutup M10. Ia menambahkan `Idempotency-Key` lewat interceptor di HTTP client, yang memasang UUID baru di setiap pengiriman. Rekaman jalur pertama menunjukkan hasilnya: server mengenali header itu, tetapi key di retry belum pernah ia lihat.

Server tidak bisa menebak bahwa dua key berasal dari satu niat. Pengenal itu hanya ada di app. Karena itu app yang harus membuatnya sekali, lalu memakainya lagi.

### Cara kerjanya: sisi app

Ada tiga aturan di app. Kodenya dijalankan di lab dengan Dart 3.11.4, `dart:io`, tanpa package.

**1. Key dibuat sekali per niat bayar.** Satu niat adalah satu tap Bayar di layar konfirmasi. Objek niat menyimpan key, tujuan, dan jumlah. Retry otomatis dan tap ulang di layar yang sama memakai objek itu lagi.

<Snippet file="labs/e3-idempotency/ledger/bayar.dart" region="niat" lang="dart" title="labs/e3-idempotency/ledger/bayar.dart" />

Key adalah UUID versi 4 (RFC 9562 bagian 5.4): 122 bit acak. Di app sungguhan generatornya `Random.secure()`. Lab memakai seed tetap supaya rekaman bisa diulang byte per byte, jadi jangan salin seed itu ke app.

**2. Retry hanya untuk kegagalan sementara, dengan batas.** Koneksi putus, timeout 10 detik, 409, 429, dan 5xx diulang. Jawaban 2xx, 400, dan 422 adalah jawaban final. Paling banyak empat percobaan.

<Snippet file="labs/e3-idempotency/ledger/bayar.dart" region="retry" lang="dart" title="labs/e3-idempotency/ledger/bayar.dart" />

**3. Sesudah percobaan terakhir, app tidak menebak.** Bila percobaan ke-4 juga gagal, app menulis "Status pembayaran belum pasti. Cek riwayat sebelum membayar lagi." Jalur ini ada di kode lab dan belum direkam.

`timeout` di app hanya berhenti menunggu. `Future.timeout` tidak membatalkan future asalnya, yang masih bisa selesai belakangan ([dokumentasi Dart](https://api.dart.dev/dart-async/Future/timeout.html), Dart 3.13.7). Request yang sudah sampai di server tetap dikerjakan, dan itu alasan retry butuh key.

### Cara kerjanya: sisi server

Server menyimpan satu baris per key. Bentuknya sama dengan migrasi `labs/api-t2/migrasi/000011_ledger_pendukung.up.sql`.

<Snippet file="labs/e3-idempotency/ledger/schema.sql" region="kunci" lang="sql" title="labs/e3-idempotency/ledger/schema.sql" />

Server mengerjakan satu request dalam dua langkah. Langkah 1 mencatat key dengan status `diproses` dan kedaluwarsa 24 jam, lalu `COMMIT` sendiri. Langkah 2 membuka transaction, mengunci baris key dengan `FOR UPDATE NOWAIT`, dan menulis jurnal, status `selesai`, serta respons di transaction yang sama. Kolom `jam_tersisa` di rekaman bernilai 24 sesudah request selesai.

Hasilnya, ada enam jawaban yang bisa diterima app. Semuanya direkam, kecuali baris terakhir.

| Kejadian | Jawaban server | Rekaman lab |
|---|---|---|
| Key baru | Dikerjakan, 201 | `key-per-niat.txt`, server #1 |
| Key selesai, sidik jari sama | 201 yang sama, tanpa jurnal baru | `key-per-niat.txt`, server #2 |
| Key sedang dikerjakan request lain | 409, app mengulang sesudah jeda | `diproses.txt` |
| Key sama, isi berbeda | 422 | `aturan.txt`, butir 2 |
| Tanpa header, atau nilai bukan UUID | 400 | `aturan.txt`, butir 3 dan 4 |
| Server mati sebelum `COMMIT` | Jurnal batal; ulangan mengerjakan dari awal | `mati-di-tengah.txt` |

Nilai header adalah String Structured Field, jadi UUID ditulis di antara tanda kutip: `Idempotency-Key: "0fa0431d…"`. Server lab hanya menerima UUID di dalam tanda kutip itu (draft bagian 2.1, RFC 9651 bagian 3.3.3). Key yang berasal dari akun lain dijawab 422 tanpa respons tersimpan, karena server mencocokkan juga `akun_id`.

#### Request kedua datang saat yang pertama belum selesai

Titik henti lab menahan transaction request #1 sebelum `COMMIT`, lalu request #2 tiba dengan key yang sama. Pencatatan key tidak menunggu lock, dan `FOR UPDATE NOWAIT` gagal dengan SQLSTATE 55P03. Server menjawab 409, dan app mengulang sesudah 461 ms.

<Snippet file="labs/e3-idempotency/output/ledger/diproses.txt" lines="22:24" title="Rekaman lab: diproses.txt, sisi app" />

<Snippet file="labs/e3-idempotency/output/ledger/diproses.txt" lines="32:39" title="Rekaman lab: diproses.txt, sisi server" />

Draft IETF bagian 2.7 menyarankan 409 untuk keadaan ini, karena client tidak perlu memperbaiki request ([draft -08](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)).

#### Server mati sebelum `COMMIT`

Jurnal, status `selesai`, dan respons ditulis di satu transaction, jadi ketiganya batal bersama. Di rekaman ini lab memutus koneksi database dengan `pg_terminate_backend`. Key tertinggal `diproses` tanpa lock, dan request kedua mengerjakannya dari awal.

<Snippet file="labs/e3-idempotency/output/ledger/mati-di-tengah.txt" lines="29:35" title="Rekaman lab: mati-di-tengah.txt, sisi server" />

Bandingkan dengan 2.13: di sana server menulis jurnal 2 lalu `COMMIT`, dan ulangan menghasilkan jurnal 3. Di sini jurnal 2 tidak pernah tersimpan, jadi ulangan memang harus mengerjakannya. Saldo Budi Rp75.000 di kedua kasus, dan app tidak bisa membedakan keduanya dari layar HP.

#### Key sama, isi berbeda

<Snippet file="labs/e3-idempotency/output/ledger/aturan.txt" lines="23:28" title="Rekaman lab: aturan.txt, sisi app" />

Server membandingkan sidik jari, yaitu sha256 dari method, path, dan body yang sudah dibaca ulang ke bentuk tetap. Spasi atau urutan field di JSON app tidak membuat ulangan dianggap permintaan lain. Penolakan 422 tidak menyimpan respons milik request lain.

### Backoff dan jitter

**Backoff** adalah jeda yang membesar di antara percobaan. App lab menunggu 200 ms × 2^(n−1) ditambah jitter acak 0–99 ms. Di rekaman `diproses.txt`, jeda sesudah percobaan 1 adalah 230 ms dan sesudah percobaan 2 adalah 461 ms.

**Jitter** adalah keacakan di jeda itu. Tanpa jitter, app yang gagal di detik yang sama mengulang di detik yang sama juga, dan lonjakan pertama terulang ([Amazon Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), 2019).

Brooker membandingkan beberapa varian di simulasi. Full Jitter, yang mengacak seluruh jeda, memakai kerja paling sedikit di antara varian yang ia ukur. Equal Jitter, yang menyisakan sebagian jeda tetap, paling buruk di antara varian ber-jitter ([AWS Architecture Blog, 2015](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)).

Jitter di app lab hanya tambahan kecil, bukan Full Jitter, dan pengaruhnya tidak diukur di lab. Di Tahap 2 beban puncak ±1,4 request per detik (Asumsi naskah), jadi kebiasaannya yang ditulis sekarang, bukan beban yang menuntutnya.

Batas jumlah percobaan juga bagian dari desain. Retry di setiap lapisan saling mengalikan: Builders' Library menghitung lima lapisan dengan tiga retry per lapisan menjadi 243 kali beban di database yang sedang gagal. Karena itu retry diletakkan di satu titik, yaitu app.

### Retry mana yang aman

RFC 9110 bagian 9.2.2 menyebut client sebaiknya tidak mengulang method yang tidak idempoten secara otomatis, kecuali ia tahu request itu idempoten atau belum pernah diterapkan. Key membuat `POST /transfers` memenuhi syarat pertama.

| Yang diterima app | Diulang? | Alasan |
|---|---|---|
| Koneksi putus, timeout | Ya | Server mungkin sudah `COMMIT`; key membuat ulangan aman (rekaman `key-per-niat.txt`) |
| 409 | Ya, sesudah jeda | Request pertama masih dikerjakan (rekaman `diproses.txt`, draft bagian 2.7) |
| 429, 503 | Ya | Kegagalan sementara; boleh membawa `Retry-After` ([RFC 6585 bagian 4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), [RFC 9110 bagian 15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4)). App lab belum membaca `Retry-After` dan lab tidak merekam kedua status ini |
| 500 | Ya, hanya karena ada key | Transaction yang gagal batal, dan key kembali bisa dikerjakan (kode lab, belum direkam) |
| 400, 422 | Tidak | Request ditolak; ulangan ditolak dengan alasan yang sama (rekaman `aturan.txt`) |
| 201 | Tidak | Jawaban final |

### At-least-once

Retry mengubah pengiriman menjadi **at-least-once**: pengirim mengulang sampai ada jawaban, sehingga penerima bisa menerima request yang sama lebih dari sekali. Dokumentasi queue standar Amazon SQS menjamin hal yang sama untuk pesan, dan menyarankan penerima siap menerima pesan ganda ([Amazon SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html)).

Key dan hasil tersimpan tidak menghentikan pengiriman ganda. Keduanya membuat efek di database terjadi sekali, walau request sampai dua kali. Konsep ini muncul lagi di Tahap 3 untuk notifikasi dan webhook ([[B10.2]]).

### ADR 14: key sekali per niat bayar, hasil disimpan 24 jam

**Kebutuhan.** Di M10, Budi membayar nasi goreng Rp25.000 dan riwayatnya mencatat dua jurnal ([[t2-m10]]). Ledger tidak menolak keduanya: tiap jurnal seimbang dan saldo tidak negatif ([[t2-ledger]]). Yang salah adalah jumlah niatnya. Bebannya kecil: ±900 transaksi per hari dan puncak ±1,4 request per detik (Asumsi naskah bagian 3b).

**Status:** diterima di minggu 2 Tahap 2, sesudah M10. Berlaku untuk jalur uang yang dikirim app: bayar ke warung dan transfer antar karyawan. Lab e3 membuktikan pola ini di server sendiri; `labs/api-t2` belum memasangnya (usulan di keputusan 517).

| | A. Tanpa key, app mencegah dobel | B. Key per request | C. Key per niat bayar, hasil disimpan | D. Dedup isi request dalam jendela waktu |
|---|---|---|---|---|
| Cara kerja | App mengunci tombol Bayar selama spinner dan tidak mengulang POST otomatis. Server tidak berubah | Interceptor HTTP memasang UUID baru di setiap pengiriman, termasuk retry. Server memakai tabel key | App membuat key sekali di objek niat. Server mencatat key, lalu menulis jurnal, status `selesai`, dan respons di satu transaction | Server menghitung sidik jari (akun, tujuan, jumlah) dan menganggap request identik dalam jendela waktu sebagai ulangan |
| Kelebihan | Tanpa tabel baru dan tanpa perubahan server. App lama tidak terganggu | Satu tempat di app, tanpa mengubah layar | Ulangan mendapat jawaban asli tanpa jurnal baru. Key sama dengan isi berbeda ditolak. Berlaku untuk tap ulang dan retry otomatis | App 1.0 dan 1.1 ikut terlindungi tanpa update |
| Kekurangan | Spinner tidak memberi tahu hasil. Sesudah app menyerah, tap berikutnya membawa request yang sama dan dijurnal lagi | Retry tampak seperti niat baru, jadi ulangan tidak dikenali. Terlihat benar di kode dan di log | Butuh tabel key, masa simpan, dan disiplin di app. App 1.0 dan 1.1 tidak mengirim key | Server tidak bisa membedakan ulangan dari niat kedua yang identik. Budi yang membeli dua nasi goreng Rp25.000 dalam satu jendela dirugikan. Panjang jendela adalah tebakan |
| Biaya operasional | Kode app kecil. Beban pindah ke Budi, yang harus memeriksa riwayat sendiri | Tabel dan job pembersih sama dengan C | Satu baris per request selama 24 jam: ≤ ±900 baris per hari (Asumsi naskah). Job pembersih belum ada di lab | Tabel sidik jari seperti C, ditambah keputusan produk: apa jawaban untuk request yang dianggap ulangan |
| Bukti | Rekaman `tanpa-key.txt`: jurnal 3. RFC 9110 bagian 9.2.2 | Rekaman `key-per-percobaan.txt`: dua jurnal, saldo Rp50.000 | Rekaman `key-per-niat.txt`, `diproses.txt`, `mati-di-tengah.txt`, `aturan.txt`. Pola sama dengan Builders' Library dan Stripe | Tidak dijalankan. Amazon SQS FIFO memakai interval 5 menit dan hash SHA-256 body ([dokumentasi](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html)) |

**Keputusan: opsi C.** Enam aturan:

1. App membuat key (UUID versi 4) sekali per niat bayar, di objek niat dan bukan di fungsi kirim. Retry otomatis dan tap ulang di layar yang sama memakai objek itu. Sesudah jawaban final, tap baru adalah niat baru dengan key baru.
2. Server mencatat key di langkah sendiri, lalu menulis jurnal, status `selesai`, dan respons di satu transaction. Key yang sama dengan isi atau pemilik berbeda dijawab 422, dan key yang sedang dikerjakan dijawab 409.
3. Ulangan atas key selesai mendapat respons tersimpan tanpa jurnal baru, termasuk penolakan aturan bisnis seperti saldo kurang. Jawaban 500 tidak disimpan, karena transaction-nya batal dan key bisa dikerjakan lagi.
4. App mengulang hanya koneksi putus, timeout 10 detik, 409, 429, dan 5xx. Paling banyak empat percobaan, jeda 200 × 2^(n−1) ms ditambah jitter 0–99 ms. Sesudahnya app menulis "status belum pasti, cek riwayat" dan tidak membayar lagi.
5. **App 1.0 dan 1.1.** Bayar tanpa header `Idempotency-Key` tetap diterima seperti server minggu 2, selama masa peralihan. Header yang ada tetapi bukan UUID tetap dijawab 400. Server mencatat setiap Bayar tanpa key. Perilaku "wajib key" (400, `aturan.txt` butir 3) dinyalakan sesudah satu minggu penuh tanpa Bayar tanpa key (Asumsi).
6. Baris key yang lewat 24 jam dihapus oleh job pembersih (`DELETE … WHERE kedaluwarsa < now()`). Job itu belum ada di lab.

**Kenapa aturan 5 begini.** Lab menolak Bayar tanpa key dengan 400 (`aturan.txt` butir 3), padahal app 1.0 dan 1.1 tidak mengirim key. Menyalakannya sekarang membuat Bayar gagal di setiap HP yang belum diperbarui. [[E1|ADR 10]] sudah menolak jalan itu: server tidak punya versi minimum atau layar wajib update, dan app 1.0 bahkan tidak mengirim versinya.

Pola [[E1|ADR 10]] dipakai lagi: tambah dulu, wajibkan kemudian. Jumlah Bayar tanpa key adalah hitungan yang ADR 10 belum punya, karena app yang mengirim key pasti app baru.

Risikonya diterima terbuka. Selama peralihan, app 1.0 dan 1.1 bisa menulis dua jurnal seperti M10.

Rekaman `tanpa-key.txt` adalah ujung itu dan `aturan.txt` ujung satunya. Perilaku di antara keduanya, key opsional, belum direkam di lab. Mengembalikannya ke "wajib" atau "opsional" adalah satu pengaturan server.

**Kenapa C, bukan A, B, atau D.**

- **A ditolak** karena mengunci tombol tidak menjawab pertanyaan Budi. Rekaman `tanpa-key.txt` menunjukkan jurnal kedua, dan tap sesudah app menyerah membawa request yang sama.
- **B ditolak** karena ia terlihat benar sambil gagal. Header ada di kedua request, tetapi server menulis dua jurnal (`key-per-percobaan.txt`). Opsi C membutuhkan tabel yang sama, jadi B tidak menghemat apa pun.
- **D ditolak** karena isi yang sama bukan bukti niat yang sama. Dua key di rekaman B punya sidik jari identik, tetapi server tidak bisa tahu apakah itu retry atau pembelian kedua. D hanya dipakai bila tidak ada app yang bisa dimintai key.

**Pre-mortem.** Bayangkan keputusan ini gagal 6 bulan lagi. Tiga penyebab yang paling mungkin:

1. Key dibuat per pengiriman lagi, misalnya sesudah library HTTP diganti. Kodenya tampak benar, dan log menunjukkan header terkirim. Pencegahannya aturan 1: key milik objek niat, satu tes app mengirim dua percobaan dan memeriksa header sama, dan checklist review di blok Kunci.
2. Key hanya ada di memori. App ditutup atau crash sesudah Budi menekan Bayar, dan saat app dibuka ia menekan lagi, dengan key baru. Lab menyimpan key di memori dan tidak merekam kasus ini. Pencegahannya: simpan niat (key, tujuan, jumlah) di penyimpanan lokal sampai jawaban final.
3. Dua niat memakai key yang sama karena generatornya tidak acak, misalnya seed tetap dari tes terbawa ke app. Bayar kedua dengan tujuan dan jumlah yang sama dijawab dengan respons pembayaran pertama: Budi melihat "berhasil" padahal tidak ada jurnal baru. Pencegahannya `Random.secure()` dan pemeriksaan pemilik di server. Kasus ini belum direkam.

**Kapan keputusan ini salah.** Saat satu niat bisa dikirim ulang lebih dari 24 jam sesudah percobaan pertama. Contohnya queue offline yang baru tersambung keesokan harinya ([[E2]]). Lab tetap menghormati key yang belum dihapus (keputusan 514), jadi job pembersih yang menghapus tepat 24 jam akan membuka celah itu.

Keputusan ini juga salah untuk jalur uang yang tidak dimulai app, seperti pencairan Jumat. Di sana tidak ada client yang membuat key.

**Yang akan merevisinya.** Pencairan warung memakai kunci dari data (periode), bukan key dari client ([[t2-job-rekonsiliasi]]). Notifikasi dan webhook di Tahap 3 memindahkan pola ini ke sisi penerima yang menerima at-least-once ([[B10.2]]).

### Cek diri

**1.** AI menulis interceptor Dio yang menambahkan `Idempotency-Key` dengan UUID baru di setiap request, termasuk retry. Aman dari M10?

<details class="success">
<summary>Jawaban</summary>

Tidak aman. Retry membawa key yang belum pernah dilihat server, jadi dikerjakan sebagai niat baru: dua jurnal dan saldo Rp50.000 (rekaman `key-per-percobaan.txt`). Perbaikannya: buat key sekali di objek niat saat Budi menekan Bayar, lalu pakai objek itu di setiap percobaan.

</details>

**2.** Server menjawab 422 saldo kurang. Budi mengisi saldo, lalu menekan Bayar lagi. Pakai key lama atau key baru?

<details class="success">
<summary>Jawaban</summary>

Key baru. Server menyimpan semua hasil sesudah key dicatat, termasuk penolakan aturan bisnis, jadi key lama akan mengulang jawaban 422 selama 24 jam. Tap baru sesudah jawaban final adalah niat baru. Perilaku ini dari kode lab (`denganKunci`) dan belum direkam.

</details>

**3.** Request kedua tiba saat request pertama belum `COMMIT`. Apa jawaban server, dan apa yang dilakukan app?

<details class="success">
<summary>Jawaban</summary>

Server menjawab 409, karena baris key sedang dikunci transaction request pertama (SQLSTATE 55P03). App mengulang dengan key yang sama sesudah jeda, dan percobaan berikutnya menerima 201 yang sama. Di rekaman `diproses.txt`, percobaan 2 dikirim 230 ms sesudah percobaan 1 dan dijawab 409. Percobaan 3 dikirim 461 ms kemudian dan dijawab 201.

</details>

**4.** Key yang sama dikirim lagi untuk pembayaran Rp30.000, padahal key itu sudah dipakai untuk Rp25.000. Apa yang terjadi?

<details class="success">
<summary>Jawaban</summary>

Server menjawab 422. Sidik jari isi request berbeda dari yang tersimpan, jadi server tidak mengirim respons milik pembayaran Rp25.000 dan tidak menulis jurnal (rekaman `aturan.txt` butir 2).

</details>

**5.** App timeout, dan Raka menyimpulkan pembayaran gagal lalu menampilkan "Gagal, coba lagi". Apa yang salah?

<details class="success">
<summary>Jawaban</summary>

Timeout hanya berarti app berhenti menunggu. Di rekaman `key-per-niat.txt`, request pertama sudah `COMMIT` sebelum response-nya hilang. App harus mengulang dengan key yang sama, atau menampilkan "status belum pasti, cek riwayat" sesudah percobaan terakhir.

</details>

### Saat me-review kode AI, cek ini

- [ ] Key dibuat sekali per niat bayar, di luar loop retry dan di luar fungsi kirim atau interceptor.
- [ ] Generator key acak (`Random.secure()`), bukan seed tetap, waktu, atau nomor urut.
- [ ] Niat (key, tujuan, jumlah) disimpan di penyimpanan lokal sampai jawaban final.
- [ ] Retry hanya untuk koneksi putus, timeout, 409, 429, dan 5xx, dengan batas percobaan dan jeda membesar plus jitter.
- [ ] Server mencocokkan key, pemilik, dan sidik jari isi. Key, jurnal, status `selesai`, dan respons ditulis dalam transaction yang benar.
- [ ] Tidak ada panggilan jaringan di dalam transaction yang memegang lock.
