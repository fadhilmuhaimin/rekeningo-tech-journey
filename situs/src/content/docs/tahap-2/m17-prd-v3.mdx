<Blok nama="Yang sebenarnya">

Pertanyaan Sinta berisi tiga pertanyaan, dan masing-masing butuh bukti yang berbeda.

**Apakah data cocok?** Tutup buku menjawabnya. Di lab api-t2, laporan membaca 1.016 buku dan semuanya cocok:

<Snippet file="labs/api-t2/output/tutup-buku.txt" lines="8:11" title="Rekaman lab: labs/api-t2/output/tutup-buku.txt, bagian A (tutup buku atas 1.016 buku)" />

Raka dan Nadia benar bahwa ini lolos. Versi kecilnya di lab b3-ledger membaca 9 buku dan 11 jurnal dengan hasil yang sama (rekaman lab `tutup-buku.txt` bagian A dan B, lab b3-ledger).

**Apakah laporannya final?** Rp0 tidak menjawabnya. Rekaman bagian C membuat laporan saat transaction [A] belum COMMIT. [A] sudah menulis jurnal top-up susulan Rp1.000 untuk Budi:

<Snippet file="labs/api-t2/output/tutup-buku.txt" lines="42:47" title="Rekaman lab: labs/api-t2/output/tutup-buku.txt, bagian C (laporan saat [A] belum COMMIT)" />

Lalu [A] COMMIT, dan laporan yang sama dijalankan lagi:

<Snippet file="labs/api-t2/output/tutup-buku.txt" lines="64:72" title="Rekaman lab: labs/api-t2/output/tutup-buku.txt, bagian C (laporan sesudah [A] COMMIT)" />

Laporan kedua menghitung 1.123 jurnal, bukan 1.122. Uang masuk Budi naik dari Rp1.020.000 ke Rp1.021.000. Buku yang tidak cocok tetap 0, jadi dua laporan yang berbeda lolos dengan angka yang sama.

Dua hal menjelaskan hasil ini. Pertama, laporan hanya melihat data yang sudah COMMIT saat querynya dimulai ([PostgreSQL 17, 13.2.1](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)), jadi jurnal [A] belum terlihat di laporan pertama. Kedua, kolom `dibuat` berisi `now()`, waktu awal transaction ([PostgreSQL 17, 9.9.5](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)), sehingga jurnal [A] tetap bertanggal sebelum laporan pertama.

Jurnal itu menulis posting dan `saldo_cache` dalam satu transaction, jadi buku Budi cocok di kedua laporan. Rp0 mengukur kecocokan data yang terlihat, bukan kelengkapannya. Di pembukuan manual pun, neraca saldo yang seimbang tidak menjamin bebas salah ([OpenStax, Principles of Accounting, bagian 3.6](https://openstax.org/books/principles-financial-accounting/pages/3-6-prepare-a-trial-balance)).

Naskah tidak menyebut apakah ada transaction terbuka saat uji coba kedua berjalan. Rp0 tidak bisa membedakan "tidak ada" dari "ada, tetapi belum terlihat". Menutup periode dengan benar butuh menunggu transaction yang masih terbuka atau tabel penutupan periode, dan keduanya belum dibuat ([[t2-tutup-buku]]).

**Apakah server cukup?** Tutup buku juga tidak menjawabnya, karena rekaman tidak mengukur beban. Hitungannya Asumsi dari `cerita.json`, bukan pengukuran:

| Besaran | Nilai | Cara hitung (semua asumsi) |
|---|---|---|
| User terdaftar (Tahap 2) | 1.000 | Seluruh kampus pusat |
| Request per hari (Tahap 2) | 12.000 | 1.000 × 30% × 40 request |
| Puncak request per detik (Tahap 2) | ±1,4 | 12.000 ÷ 86.400 × 10 |
| Kepekaan: semua request dalam satu jam | ±3,3 | 12.000 ÷ 3.600 |

Rumusnya sama dengan [[t1-m8]]. Puncak sekarang ±1,4 request per detik, atau satu request kira-kira tiap 0,7 detik. Beban PRD v3 dihitung dengan rumus yang sama di [[t2-estimasi]].

Angka itu tidak membuktikan server cukup. Lab Tahap 2 tidak punya perkakas load test (dicari k6, wrk, locust, dan perkakas serupa di sepuluh lab pada 2026-10-25, tanpa hasil). Berapa request per detik yang sanggup dilayani VPS belum pernah diukur (Tidak dijalankan). Yang bisa dikatakan hanya ini: belum ada angka yang menyuruh membeli server hari ini.

**Dua hal yang belum pernah diuji.** Naskah menyebutnya: pekerjaan lambat di dalam request, dan banyak server sekaligus. Notifikasi yang dikirim di dalam request berarti request Budi menunggu layanan lain. PRD v2 menundanya ke v3 ([[t2-prd]]), dan kode server api-t2 tidak memanggil layanan lain selain database.

Untuk banyak server, rekaman api-t2 memakai satu proses (`server: ./api-t2`). Di antara lab Tahap 2, dua instance hanya direkam di c4-ratelimit, untuk batas laju ([[t2-login-aman]]). api-t2 sendiri belum pernah dijalankan dengan dua server (Tidak dijalankan). [[t2-jembatan]] meminta kamu menebak mana yang pecah lebih dulu.

**Delapan masalah, bukan satu kapasitas.** Sebelum PRD v3, Tahap 2 sudah punya delapan masalah. Tabel ini merangkum penyebabnya dari halaman masing-masing:

| Masalah | Yang rusak |
|---|---|
| [[t2-m9]] | Dua transaction membaca saldo yang sama sebelum salah satunya menulis |
| [[t2-m10]] | Server tidak mengenali permintaan yang diulang |
| [[t2-m11]] | Query riwayat yang salah: N+1 dan tanpa index |
| [[t2-m12]] | Pagination offset bergeser saat ada transaksi baru |
| [[t2-m13]] | Lock dari ALTER dan perubahan skema yang merusak app lama |
| [[t2-m14]] | Batas harian hilang saat merge, tanpa review dan tes yang menjaganya |
| [[t2-m15]] | Job berjalan dua kali, sehingga ledger dan file bank tidak sama |
| [[t2-m16]] | Kunci per akun mengunci pemiliknya, dan password sementara tidak diganti |

Tidak satu pun penyebabnya adalah server yang kehabisan tenaga.
