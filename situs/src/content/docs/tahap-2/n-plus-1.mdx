## Inti

N+1 query terjadi saat kode mengirim satu query untuk daftar, lalu satu query lagi untuk setiap baris di daftar itu.

<Rantai data={intiDiagram} ringkas />

Riwayat Budi di minggu 3 bekerja begitu. Satu query mengambil 20 transaksi terakhir, lalu 20 query mencari nama lawan setiap transaksi. Rekaman lab b2-query memakai data satu tahun (760.448 posting). Laporan harian Ani mengirim 195 query untuk 194 baris, dan seluruh riwayat Budi 3.893 query untuk 3.892 baris.

Jumlah query mengikuti jumlah baris, bukan ukuran tabel, jadi N+1 sulit terlihat di data kecil. Kalau nama lawan diminta di query yang sama, hasilnya baris yang sama dengan 1 query. Itu memperbaiki N+1 saja: query daftarnya masih membaca terlalu banyak baris, dan itu dibahas di [[B2.3]].

Jalur utama berhenti di 21 query. Query 2 sampai 21 berbeda hanya di nomor jurnal, dan setiap query kecil: rata-rata ±0,5 ms (1.936,4 ms untuk 3.893 query, `n1.txt` bagian E, pembanding). Yang menentukan waktu adalah jumlahnya.

Nyalakan **Ubah satu hal**: nama lawan dicari di query yang sama. Jalurnya jadi dua langkah, dan lima baris pertamanya sama dengan jalur N+1 (`n1.txt` bagian C). Pencarian per baris tidak hilang. Ia pindah ke dalam database, tempat satu baris tidak membutuhkan perjalanan bolak-balik dari handler.

### Kenapa ini ada

Di [[t2-m11]], Raka menyalakan log semua statement dan menghitung 21 baris log untuk satu halaman riwayat. Kode yang mencari nama lawan per transaksi mudah ditulis, mudah dibaca, dan hasilnya benar. Misalnya di laptop dengan 10 transaksi uji (Ilustrasi, bukan rekaman), layarnya terasa instan, jadi tidak ada tanda bahwa jumlah query tumbuh.

Pola ini muncul dalam dua bentuk. Bentuk pertama adalah query di dalam loop atas hasil query lain. Bentuk kedua adalah ORM dengan lazy loading: kode hanya mengakses `posting.jurnal`, dan library mengirim satu query setiap kali relasi itu pertama dipakai.

Kalau kamu pernah memanggil API detail di dalam `ListView.builder` untuk setiap baris, polanya sama. Bedanya di backend, setiap query memegang satu koneksi database selama berjalan, dan jumlah koneksinya terbatas ([[B2.5]]).

### Cara kerjanya

**1. Jumlah query yang menentukan waktu, bukan satu query.** Satu query nama lawan kecil dan benar. Seluruh riwayat Budi butuh 3.893 query dan ±1.936 ms, sedangkan satu query yang mengembalikan baris yang sama selesai dalam ±31 ms (`n1.txt` bagian E, pembanding). Kode client lab menulis kedua cara dalam dua fungsi:

<Snippet file="labs/b2-query/run_ledger.py" lines="64:73" lang="python" title="Kode client lab: labs/b2-query/run_ledger.py (Python, psycopg 3)" />

**2. Jumlah query mengikuti jumlah baris.** Lab menghitung query dari dua sisi: penghitung di client, dan log PostgreSQL dengan `log_statement = all` ([PostgreSQL 17, log_statement](https://www.postgresql.org/docs/17/runtime-config-logging.html)). Kedua hitungan sama di setiap permintaan.

<Snippet file="labs/b2-query/output/ledger/n1.txt" lines="41:52" title="Rekaman lab: labs/b2-query/output/ledger/n1.txt, bagian D (jumlah query)" />

Polanya 1 ditambah jumlah baris untuk N+1, dan 1 untuk satu query. Catatan di rekaman yang sama: index tidak mengubah jumlah query.

**3. Waktu punya dua penyebab, dan masing-masing punya perbaikan.** Kolom kiri tabel ini memakai database lab tanpa index riwayat, keadaan sebelum M11. Kolom kanan memakai index riwayat yang diputuskan di [[B2.3]].

<Snippet file="labs/b2-query/output/ledger/n1.txt" lines="54:65" title="Rekaman lab: labs/b2-query/output/ledger/n1.txt, bagian E (waktu pembanding, bukan janji)" />

Untuk 20 baris, satu query (27,4 ms) hampir tidak lebih cepat dari N+1 (30,5 ms). Query daftarnya sendiri membaca 3.892 posting dan 380.224 jurnal. EXPLAIN ANALYZE di `index.txt` bagian B mencatat ±31 ms, dari pengukuran lain dengan metode berbeda, jadi bandingkan besarnya, bukan selisih satu milidetik. Untuk 194 baris selisihnya 106,1 lawan 9,3 ms, dan untuk 3.892 baris 1.936,4 lawan 30,6 ms.

Di kolom kanan, N+1 tetap lebih lambat: 10,4 lawan 1,4 ms untuk halaman pertama. Kedua perbaikan berdiri sendiri: index tidak mengubah jumlah query, dan satu query tidak mengubah baris yang dibaca query daftar. M11 membawa kedua masalah, jadi keduanya harus diperbaiki. Waktu di rekaman datang dari satu mesin lab yang dipakai lab lain bersamaan.

**4. Jaringan menambah biaya per query.** Di lab tidak ada jaringan antara handler dan database. Kalau database ada di mesin lain, setiap query membayar paling sedikit satu round trip. Untuk query yang dikirim berurutan seperti di lab, tambahan = jumlah query × RTT. Dengan RTT 1 ms (Asumsi, bukan rekaman), 21 query menambah 21 ms, 3.893 query menambah 3,9 detik, dan 1 query menambah 1 ms.

Naskah Tahap 2 memakai satu server, jadi tambahan ini belum terjadi. Rumusnya berlaku begitu database pindah ke mesin sendiri.

### Cara menemukannya

Hitung query per request. Waktu saja menyesatkan: di data kecil, N+1 hampir secepat satu query (30,5 lawan 27,4 ms di atas).

1. Hitung query dari dua sisi seperti lab: penghitung di client dan log PostgreSQL. Kedua hitungan harus sama.
2. Cari pola di log: query yang sama dengan parameter berbeda, berulang puluhan kali dalam satu request.
3. Tulis tes yang memanggil endpoint dengan 5 baris data lalu 50 baris, dan mengharapkan jumlah query yang sama. N+1 membuat kedua hitungan berbeda.

### Cara memperbaikinya

| Cara | Query | Catatan |
|---|---|---|
| Satu query dengan JOIN | 1 | Dipakai lab (`n1.txt` bagian B): `LEFT JOIN` dan `LATERAL ... LIMIT 1` |
| Dua query: daftar, lalu relasi untuk semua baris sekaligus | 2 | Tidak dijalankan di lab; `with()` Laravel dan `prefetch_related` Django bekerja begini |

Query lab ditulis hati-hati karena JOIN yang salah mengubah hasil tanpa error. Tiga hal yang dijaga:

1. **Baris tanpa pasangan.** `JOIN` biasa membuang baris dari tabel kiri yang tidak punya pasangan ([PostgreSQL 17, joined tables](https://www.postgresql.org/docs/17/queries-table-expressions.html)). Lawan transaksi tunjangan adalah buku sistem tanpa akun, jadi query lab memakai `LEFT JOIN akun`. Dengan `JOIN` biasa, baris "Tunjangan makan" hilang dari riwayat (Tidak dijalankan di lab).
2. **Baris yang menggandakan.** `JOIN` ke tabel yang punya beberapa pasangan menghasilkan satu baris per pasangan, sesuai dokumentasi yang sama. Satu jurnal punya minimal dua posting, jadi query lab mengambil satu posting lawan lewat `LATERAL (... ORDER BY q.id LIMIT 1)`.
3. **Hasil yang sama.** Lab membandingkan baris kedua cara: urutan, jenis, lawan, dan jumlah (`n1.txt` bagian C). Tes jumlah query saja tidak menangkap baris yang hilang.

Yang sama di semua stack: relasi yang diakses di dalam loop memicu query baru. Yang berbeda: apakah query itu terlihat di kode, dan cara meminta relasi sekaligus.

### Trade-off: kapan pakai apa

| Pilihan | Kelebihan | Kekurangan |
|---|---|---|
| Lazy loading | Kode paling ringkas | Query = 1 + jumlah baris, dan tidak terlihat di kode |
| Satu query dengan JOIN | 1 query di client dan di log (rekaman) | JOIN biasa membuang baris tanpa pasangan dan bisa menggandakan baris; query lebih panjang |
| Dua query, relasi untuk semua baris | Tanpa menggandakan baris induk; ORM menyediakannya (Tidak dijalankan) | 2 query, dan daftar ID bisa panjang |
| Cache hasilnya | Cepat saat isi cache ada | Cache kosong tetap mengirim 3.893 query untuk seluruh riwayat; data bisa stale; penyebabnya tersembunyi |
| Server lebih besar | Tanpa mengubah kode | Jumlah query tetap 1 + jumlah baris |

Untuk daftar yang membawa relasi, mulai dari satu query. Pakai dua query bila relasinya banyak per baris dan menggandakan baris induk terlalu besar. Keputusan untuk riwayat Rekeningo, termasuk index, ditulis sebagai ADR 15 di [[B2.3]].

### Cek diri

**1.** Endpoint riwayat memakai pagination 20 baris per halaman. Apakah N+1 masih masalah?

<details class="success">
<summary>Jawaban</summary>

Masih. Halaman pertama mengirim 21 query di rekaman, setiap kali halaman dibuka. Pagination membatasi N, tidak menghilangkan N+1. Laporan Ani yang membaca 194 baris sekaligus mengirim 195 query.

</details>

**2.** Di rekaman, halaman pertama tanpa index riwayat memakai 30,5 ms dengan N+1 dan 27,4 ms dengan satu query. Apakah itu berarti N+1 tidak perlu diperbaiki?

<details class="success">
<summary>Jawaban</summary>

Tidak. Query daftarnya sendiri memakai ±31 ms, jadi waktu halaman pendek menyembunyikan jumlah query. Pada 194 baris selisihnya 106,1 lawan 9,3 ms, dan pada 3.892 baris 1.936,4 lawan 30,6 ms. Ukur jumlah query, bukan hanya waktu.

</details>

**3.** Raka mengganti `LEFT JOIN akun` menjadi `JOIN akun` supaya query terlihat rapi. Tes jumlah query tetap lulus dengan 1 query. Apa yang rusak?

<details class="success">
<summary>Jawaban</summary>

Baris yang lawannya buku sistem tanpa akun, seperti "Tunjangan makan", hilang dari riwayat tanpa error. Aturan `JOIN` biasa membuang baris yang tidak punya pasangan. Tes jumlah query tidak menangkapnya; butuh tes yang membandingkan baris dengan cara lama (Tidak dijalankan di lab).

</details>

**4.** Raka ingin memasang cache untuk riwayat sebelum memperbaiki query. Kenapa urutannya salah?

<details class="success">
<summary>Jawaban</summary>

Beban puncak Tahap 2 ±1,4 request per detik, jadi masalahnya bukan beban. Setiap kali cache kosong, seluruh riwayat Budi tetap mengirim 3.893 query. Cache juga menyembunyikan penyebabnya dan menambah risiko data stale, yaitu data yang sudah tidak terbaru.

</details>

### Saat me-review kode AI, cek ini

- [ ] Tidak ada query atau akses relasi di dalam loop atas hasil query lain.
- [ ] Relasi yang dipakai di response diminta bersama query daftar (`JOIN`, `with`, `select_related`, `prefetch_related`, `include`).
- [ ] Ada tes yang menghitung query untuk 5 dan 50 baris, dan mengharapkan hasil yang sama.
- [ ] `JOIN` pengganti N+1 memakai `LEFT JOIN` untuk relasi yang boleh kosong, dan tidak menggandakan baris induk.
- [ ] Daftar punya batas baris (`LIMIT` atau kursor).
