### Kenapa dua PR hijau membuat `main` merah

CI di pull request tidak menguji cabang sendirian. Dokumentasi GitHub menulis bahwa untuk event `pull_request`, `GITHUB_SHA` adalah merge commit terakhir di `refs/pull/<nomor>/merge`, yaitu gabungan PR dengan branch tujuannya ([GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

Gabungan itu dibuat dengan `main` yang ada saat CI berjalan. Workflow hanya berjalan lagi bila PR-nya `opened`, `synchronize`, atau `reopened` (daftar bawaan di dokumentasi yang sama). Dari daftar itu disimpulkan bahwa merge PR lain ke `main` tidak mengulang CI PR Nadia; ini penalaran dari dokumentasi, bukan hasil rekaman GitHub.

<Rantai data={gabunganDiagram} />

Aturan "Require branches to be up to date before merging" menutup celah itu. Dokumentasi branch protection menulis bahwa cabang harus mutakhir dengan branch tujuan sebelum merge bila opsi ini menyala ([GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Pembaruan itu mendorong commit baru, CI berjalan lagi, dan kali ini ia menguji gabungan kedua perubahan.

Hasilnya ada di rekaman bagian C. PR Nadia tertinggal satu commit, diperbarui, dan CI menolaknya. Tanpa syarat itu (varian bagian C), gabungan pertama kali diuji di `main`.

### Branch protection dan CODEOWNERS

Branch protection memaksa aturan tim di sisi GitHub, jadi tidak bergantung pada niat orang. CODEOWNERS memberi tahu GitHub siapa yang diminta me-review PR yang menyentuh bagian tertentu.

File CODEOWNERS contoh untuk Rekeningo memakai dua orang di setiap baris:

<Snippet file="labs/api-t2/deploy/CODEOWNERS" title="labs/api-t2/deploy/CODEOWNERS" />

Dokumentasi GitHub menaruh file ini di `.github/`, di root repo, atau di `docs/`, dan memakai aturan seperti `.gitignore` dengan pola terakhir yang cocok menang. Beberapa pemilik harus ada di baris yang sama, dan persetujuan salah satunya cukup ([GitHub Docs: About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)). Penulis PR tidak bisa menyetujui PR-nya sendiri ([GitHub Docs: Approving a pull request with required reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews)). Jadi PR Raka menunggu Nadia, dan sebaliknya.

Pengaturan `main` yang dipilih ADR 18 ditulis sebagai isi permintaan REST. Ini contoh, tidak dijalankan: mengubah branch protection butuh izin admin repo, dan halaman ini tidak mengubah pengaturan repo mana pun ([GitHub Docs: REST, branch protection](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection)).

<Snippet lang="json" title="PUT /repos/{owner}/{repo}/branches/main/protection (Tidak dijalankan)" code={`{
  "required_status_checks": { "strict": true, "checks": [{ "context": "tes" }] },
  "required_pull_request_reviews": {
    "required_approving_review_count": 1,
    "require_code_owner_reviews": true
  },
  "enforce_admins": true,
  "restrictions": null,
  "allow_force_pushes": false
}`} />

| Pengaturan | Arti menurut dokumentasi | Untuk apa di Rekeningo |
|---|---|---|
| `required_status_checks.strict` | "Require branches to be up to date before merging" | Hasil gabungan dua PR diuji sebelum merge |
| `required_status_checks.checks` | Status check yang harus berhasil sebelum merge | Job `tes` di `ci.yml` |
| `required_approving_review_count` | Jumlah approval yang dibutuhkan | Satu orang selain penulis |
| `require_code_owner_reviews` | "Blocks merging pull requests until code owners review them" | PR yang menyentuh `internal/service/` menunggu pemilik |
| `enforce_admins` | "Enforce all configured restrictions for administrators" | Aturan berlaku juga untuk Raka sebagai pemilik repo |
| `allow_force_pushes` | Force push ke branch ini | Mati; GitHub memblokirnya di branch terlindungi secara bawaan |

*Ketersediaan di repo privat [perlu verifikasi]:* halaman REST menulis bahwa branch protection tersedia di repo publik dengan GitHub Free. Di repo publik dan privat, ia tersedia dengan Pro, Team, Enterprise Cloud, dan Enterprise Server. Halaman plan GitHub menaruh "Protected branches", "Required pull request reviewers", dan "Code owners" di fitur repo privat untuk Pro dan Team, dan tidak mendaftarkannya untuk Free. Apakah repo Rekeningo publik atau privat, dan plan apa yang dipakai, tidak ada di naskah.

### ADR 18: review satu orang lain, tes aturan uang yang wajib berjalan, dan main yang dilindungi

**Kebutuhan.** Di M14, dua cabang digabung tanpa konflik dan batas harian hilang dari `Kirim` ([[t2-m14]]). Server dari kode tanpa pemeriksaan menjawab `201` untuk kiriman Rp800.000 dengan `sisa_batas_harian` bernilai `-300000`. Ledger tetap seimbang, jadi tidak ada lapisan lain yang menolaknya.

Tes yang memanggil `periksaBatas` langsung tetap lolos. Dari 20 tes dengan PostgreSQL, hanya dua yang gagal (rekaman `m14.txt` bagian C). Tanpa PostgreSQL, 8 tes lolos dan 12 dilewati, dan `go test` keluar 0.

**Status:** diterima di minggu 5 Tahap 2, sesudah M14. Berlaku untuk setiap perubahan di `internal/service/`, `migrasi/`, dan `deploy/`.

**Beda dengan naskah.** Naskah menulis tes integrasi dengan Testcontainers. Lab memakai PostgreSQL dari docker compose, dan CI contoh memakai service container. Testcontainers tidak dijalankan.

PROPOSAL menaruhnya di Tahap 3. Naskah yang menang, jadi halaman ini menjelaskan keduanya.

| | A. Tanpa proses | B. Review manual saja | C. Review, tes wajib, branch mutakhir, CODEOWNERS | D. Trunk-based dengan feature flag, review sesudah |
|---|---|---|---|---|
| Cara kerja | Dua orang mengubah `main` sesuai ingatan masing-masing | Tiap PR dibaca satu orang lain. CI menjalankan tes yang ada, dan tes aturan uang tidak diwajibkan | PR wajib di-review. Tes lewat `Kirim` ke PostgreSQL wajib berjalan dan tidak boleh dilewati. Branch harus mutakhir. CODEOWNERS meminta pemilik | Commit kecil langsung ke `main`, aturan baru di balik flag, review dibaca sesudahnya |
| Kelebihan | Tanpa proses, tanpa menunggu | Pengetahuan menyebar, dan salah ketik tertangkap | Hasil gabungan diuji sebelum masuk. Aturan tidak bergantung pada ingatan, dan penjaganya berjalan sendiri | Perubahan masuk cepat. Flag bisa dimatikan tanpa deploy |
| Kekurangan | M14 itu sendiri | Kedua diff tampak wajar, dan tes fungsi tetap hijau | PR menunggu CI dan orang lain. Saat satu engineer tidak ada, yang lain tidak bisa me-merge PR-nya sendiri. Tes DB menambah waktu CI | Kode yang salah sudah di `main` saat CI merah. Flag tidak melindungi pagar yang dihapus |
| Biaya operasional | Nol | Waktu satu orang per PR | Waktu review, menit CI per PR, dan pengaturan GitHub yang harus dijaga. Menit CI belum diukur lab | Sistem flag, plus kebiasaan membaca commit sesudahnya |
| Bukti | M14 dan `m14.txt` | `tim.txt` bagian B: 1 file, 3 baris dihapus di kedua PR, CI hijau, 0 pemanggil | `tim.txt` bagian C, variannya, dan E | `tim.txt` bagian D: `main` merah sesudah merge |

**Keputusan: opsi C.** Enam aturan:

1. Tidak ada commit langsung ke `main`. Perubahan masuk lewat pull request.
2. Setiap PR di-review satu orang selain penulisnya. CODEOWNERS meminta review otomatis untuk `internal/service/` dan `migrasi/`.
3. Tes aturan uang melewati pintu masuk (`Kirim`, bukan hanya `periksaBatas`) dan berjalan di PostgreSQL sungguhan. CI mengisi `TES_DB_WAJIB=1`, dan langkah CI gagal bila ada tes dilewati.
4. Status check `tes` harus berhasil, dan cabang harus mutakhir dengan `main` sebelum merge. Hasil gabungan diuji ulang oleh CI.
5. Setiap aturan uang baru masuk bersama tes yang gagal bila pemanggilnya dihapus. Tes fungsi aturan boleh menyertainya, tetapi tidak menggantikannya.
6. Force push mati di `main`, dan aturan berlaku juga untuk admin.

**Kenapa C, bukan B.** Review manual membaca diff PR itu sendiri. Rekaman B mencatat bahwa diff kedua PR sama: satu file, tiga baris dihapus, dan CI hijau. Pereview tidak melihat hasil gabungannya, dan tes fungsi tidak melihat bahwa pemanggilnya hilang.

- **A ditolak** karena itulah M14: dua orang, satu repo, dan ingatan sebagai satu-satunya penjaga.
- **D ditolak** karena rekaman D menunjukkan `main` sudah merah saat kesalahan terdeteksi. Feature flag mematikan fitur baru, bukan pagar yang hilang; ini penalaran sendiri dari rekaman, bukan tes flag.

**Pre-mortem.** Bayangkan keputusan ini gagal 6 bulan lagi. Tiga penyebab yang paling mungkin:

1. Review menjadi formalitas. Dua orang saling percaya dan menyetujui diff tiga baris dalam hitungan menit. Pencegahannya aturan 5: pagar uang dijaga tes, bukan pembacaan. Pereview diminta bertanya apakah ada tes yang gagal bila baris itu dihapus, dan bagian E, kasus 4, menunjukkan jawabannya bisa dibuktikan. Kebiasaan reviewnya sendiri tidak direkam.
2. Tes dimatikan dengan niat baik karena sering merah. Pencegahannya langkah CI yang menggagalkan `--- SKIP`; bagian E, kasus 5, merekamnya. Tes yang flaky diperbaiki, bukan dilewati.
3. Aturan hanya ada di pengaturan GitHub, tidak di repo. Pengaturan bisa berubah, atau hilang saat repo dipindah. Pencegahannya isi permintaan di atas disimpan di repo sebagai dokumen, dan pengaturan dicocokkan dengannya tiap kuartal. Pengaturan GitHub tidak direkam di lab.

**Kapan keputusan ini salah.** Tiga tanda:

1. Review menjadi formalitas: PR disetujui tanpa komentar dan tanpa pernah menemukan masalah.
2. Tim tumbuh ke tiga orang atau lebih. Persetujuan salah satu pemilik di CODEOWNERS tetap sah, tetapi tidak lagi berarti dibaca orang yang paham.
3. Tes DB melambat sampai orang mencari jalan memutar. Ambang 10 menit per PR adalah Asumsi, dan lama tes belum diukur lab.

**Yang akan merevisinya.** Tahap 3 menambah staging dan dua instance server. PROPOSAL menaruh integration test dengan Testcontainers, migration dry-run, dan deploy staging otomatis di tahap itu. Tes saja tidak melihat kebenaran uang di lingkungan nyata, jadi rekonsiliasi di [[t2-job-rekonsiliasi]] menjaga hal yang tidak bisa dijaga PR.

### Sengaja belum dilakukan

| Yang ditunda | Kenapa ditunda | Muncul lagi di |
|---|---|---|
| Dua approval per PR | Penulis tidak bisa menyetujui PR-nya sendiri, jadi dengan dua engineer hanya ada satu pereview dan dua approval tidak pernah terpenuhi | Bila tim tiga orang atau lebih |
| Merge queue | Dua orang jarang punya lebih dari satu PR terbuka sekaligus; syarat mutakhir sudah menguji hasil gabungan | Bila PR terbuka sering tertinggal dari `main` |
| Testcontainers | Satu service container PostgreSQL cukup untuk satu schema tes; naskah menyebutnya, dan lab tidak membutuhkannya | Bila tes butuh database per tes, Redis, atau container lain |
| Staging otomatis | Deploy Tahap 2 tetap satu perintah di VPS, sama seperti ADR 9 | Tahap 3 |
| Uji mutasi otomatis di CI | Mutasi satu baris dilakukan manual di lab (M14); alat uji mutasi menambah komponen untuk satu aturan | Belum dijadwalkan |

### Saat me-review kode AI, cek ini

- [ ] PR yang menghapus atau memindahkan kode aturan uang menyertakan tes yang gagal bila pemanggilnya dihapus.
- [ ] Tidak ada `t.Skip`, `skip`, atau tes yang dimatikan di folder tes aturan uang tanpa alasan tertulis dan tanggal perbaikan.
- [ ] Workflow CI mempertahankan `TES_DB_WAJIB`, database PostgreSQL sungguhan, dan syarat bahwa status check `tes` berhasil.
- [ ] Perubahan pengaturan `main` (status check, mutakhir, force push) tercatat di repo dan diperiksa pemilik.
