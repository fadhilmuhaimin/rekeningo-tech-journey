## Inti

Pencairan adalah job tiap Jumat 15.00: saldo warung pindah ke kas pencairan, lalu masuk satu file untuk bank.

<Rantai data={intiDiagram} ringkas />

Tidak ada user yang mengirim request. Server menjalankan job pada jamnya, lalu membaca saldo setiap warung dari jumlah posting. Untuk setiap warung, job menulis satu jurnal pencairan: buku warung berkurang, dan buku `kas_pencairan` bertambah sebanyak itu. Di rekaman lab `benar.txt` bagian A (lab t2-pencairan), 12 warung bersaldo Rp2.450.000, dan Warung Ani Rp310.000.

Lalu job membuat satu file CSV, satu baris per warung, yang diunggah Keuangan ke bank dengan tangan. Sejak itu uang yang sama tercatat di dua tempat: ledger di database dan file di disk. Bagian C rekaman yang sama mencatat file 12 baris Rp2.450.000 dan mutasi `kas_pencairan` +Rp2.450.000. Pak Hadi membandingkan kedua angka itu saat tutup buku.

### Baris PRD

| Prioritas | Fitur | Keterangan |
|---|---|---|
| P0 | Pencairan warung terjadwal | Setiap Jumat 15.00: saldo warung dicairkan; Keuangan menerima satu file transfer untuk diunggah ke bank (belum ada integrasi bank) |

Tujuan PRD v2 untuk fitur ini: pencairan warung terjadwal tanpa kerja admin. Di Tahap 1, warung menunggu admin mentransfer pencairan dengan tangan ([[t2-prd]]). Menurut PRD, warung berhenti memakai Rekeningo kalau pencairan terlambat atau jumlahnya beda.

<PetaFitur data={petaPencairan} />

Berbeda dengan bayar dan transfer, fitur ini bekerja tanpa request. Tidak ada app yang menunggu jawaban, jadi tidak ada layar yang menampilkan error kalau job gagal. Integrasi bank langsung, dashboard web untuk warung, dan notifikasi push bukan lingkup PRD v2.

</Blok>

Jadi hasil job bergantung pada kapan ia jalan. PRD menulis "setiap Jumat 15.00", tapi tidak menulis pembayaran pukul 15.05 milik Jumat yang mana. ### Di stack lain

**Skenario:** job pencairan dijalankan setiap Jumat 15.00 WIB di satu server. Tidak ada tab yang dijalankan, karena lab menjalankan job sebagai perintah tanpa jadwal. Setiap tab dicek ke dokumentasi pada 2026-10-24.

Yang sama di semua stack: jadwal memanggil kode job, bukan endpoint, dan zona waktunya harus ditulis. Yang berbeda: tempat jadwal ditulis, dan zona waktu bawaannya. WIB adalah UTC+7, jadi 15.00 WIB sama dengan 08.00 UTC.

<Fragment slot="t0">

*Tidak dijalankan. Lab menjalankan binary job ini (Go 1.27.1, pgx v5.11.0) tanpa jadwal. Unit dicek ke [systemd.timer(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html) dan [systemd.time(7)](https://www.freedesktop.org/software/systemd/man/latest/systemd.time.html), systemd 262.*

<Snippet lang="ini" code={`# /etc/systemd/system/pencairan.timer
[Timer]
OnCalendar=Fri *-*-* 15:00:00 Asia/Jakarta
Persistent=true

[Install]
WantedBy=timers.target

# /etc/systemd/system/pencairan.service
[Service]
Type=oneshot
# Skrip pembungkus menghitung minggu ISO, lalu menjalankan pencairan -periode <minggu> -dir <folder>
ExecStart=/opt/rekeningo/pencairan-jumat.sh`} />

**Yang berbeda di stack ini:** Go tidak punya penjadwal bawaan, jadi jadwal dipegang systemd di server. Zona waktu ditulis di `OnCalendar`. Dengan `Persistent=true`, jadwal yang terlewat saat server mati dijalankan begitu timer aktif lagi, dan job itu membaca saldo saat itu.

</Fragment>
<Fragment slot="t1">

*Tidak dijalankan. Dicek ke [node-postgres: Pool](https://node-postgres.com/apis/pool), `pg` 8.23.1.*

<Snippet lang="js" code={`// job/pencairan.mjs: dipanggil timer systemd yang sama dengan tab Go
import pg from "pg";

const pool = new pg.Pool();
try {
  await cairkan(pool, process.argv[2]); // jurnal per warung, lalu file
} finally {
  await pool.end();
}`} />

**Yang berbeda di stack ini:** pool yang masih memegang koneksi membuat proses Node tetap hidup. Karena itu skrip job menutupnya dengan `pool.end()`, supaya proses berakhir sesudah job selesai.

</Fragment>
<Fragment slot="t2">

*Tidak dijalankan. Dicek ke [Laravel 13.x: Task Scheduling](https://laravel.com/docs/13.x/scheduling).*

<Snippet lang="php" code={`// routes/console.php
use Illuminate\\Support\\Facades\\Schedule;

Schedule::command('pencairan:jalankan')
    ->fridays()
    ->at('15:00')
    ->timezone('Asia/Jakarta');`} />

<Snippet lang="bash" code={`# satu baris crontab di server
* * * * * cd /path-to-your-project && php artisan schedule:run >> /dev/null 2>&1`} />

**Yang berbeda di stack ini:** jadwal tinggal di kode, jadi ikut review. Server hanya butuh satu baris cron yang memanggil `schedule:run` setiap menit. Zona waktu ditulis per task dengan `timezone()`, atau untuk semua task lewat `schedule_timezone` di config `app`.

</Fragment>
<Fragment slot="t3">

*Tidak dijalankan. Dicek ke [Django 6.1: custom management commands](https://docs.djangoproject.com/en/6.1/howto/custom-management-commands/) dan [Django 6.0: Tasks](https://docs.djangoproject.com/en/6.0/topics/tasks/).*

<Snippet lang="python" code={`# rekening/management/commands/pencairan.py
from django.core.management.base import BaseCommand

class Command(BaseCommand):
    def add_arguments(self, parser):
        parser.add_argument("periode")  # mis. 2026-W43

    def handle(self, *args, **options):
        cairkan(options["periode"])  # jurnal per warung, lalu file`} />

**Yang berbeda di stack ini:** Django tidak punya penjadwal berkala bawaan. Tasks framework yang baru di Django 6.0 mengantre pekerjaan, tetapi tidak menyediakan worker untuk menjalankannya, dan dokumentasinya tidak menyebut jadwal berkala. Jadi job ditulis sebagai management command, lalu timer systemd tab Go menjalankan `python manage.py pencairan <minggu>`.

</Fragment>
<Fragment slot="t4">

*Tidak dijalankan. Dicek ke [Serverpod: Recurring tasks](https://docs.serverpod.dev/concepts/scheduling/recurring-tasks), `serverpod` 4.0.4.*

<Snippet lang="dart" code={`// pencairan.jalankan: future call buatan sendiri; API ini dibuat generator Serverpod
await pod.futureCalls
    .callRecurring(identifier: 'pencairan-jumat')
    .cron('0 8 * * 5') // Jumat 08.00 UTC = 15.00 WIB
    .pencairan
    .jalankan();`} />

**Yang berbeda di stack ini:** jadwal berjalan di dalam server Serverpod, dan ekspresi cron dibaca dalam UTC. Bila server mati saat jadwal tiba, jalan itu dilakukan sekali sesudah server hidup lagi.

</Fragment>
<Fragment slot="t5">

*Tidak dijalankan. Dicek ke [Supabase Cron](https://supabase.com/docs/guides/cron), [pg_cron](https://github.com/citusdata/pg_cron), dan [PostgreSQL 17: COPY](https://www.postgresql.org/docs/17/sql-copy.html).*

<Snippet lang="sql" code={`-- pencairan_jumat(): fungsi SQL buatan sendiri yang menulis jurnal per warung
SELECT cron.schedule('pencairan-jumat', '0 8 * * 5', 'SELECT pencairan_jumat()');`} />

**Yang berbeda di stack ini:** pg_cron menjalankan SQL di dalam database, dalam waktu GMT kecuali `cron.timezone` diubah. Fungsi itu bisa menulis jurnal, tetapi `COPY` ke file di server hanya boleh untuk superuser atau role `pg_write_server_files`. Jadi file untuk Keuangan dibuat proses lain di luar database.

</Fragment>
