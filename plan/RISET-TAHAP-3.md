# Riset Tahap 3 · Enam kota
Dikerjakan 2026-10-25, skill riset-tahap (hierarki bukti dari analisis-kritis). Semua tautan dibuka 2026-10-25; versi paket dari GitHub Releases (`gh api`), npm, pub.dev, dan pkg.go.dev hari itu. Cakupan dari PROPOSAL "Enam tahap dalam satu tabel" (Tahap 3: outbox, cache, rate limit, observability, staging, dashboard merchant; sengaja belum: microservices, k8s) dan registry `tahap[2]`. Replika baca bukan Tahap 3 menurut PROPOSAL (Tahap 5). Rekaman lab lama dirujuk dengan path, tidak dijalankan ulang. Stack Overflow ditolak alat pencarian, jadi jebakan diambil dari GitHub issues yang dibuka satu per satu.

## Kasus industri untuk ADR
- R3-24 Outbox dan worker di database: 37signals, "Introducing Solid Queue" (2023-12-18) dan "Solid Queue 1.0" (2024-09-26), dev.37signals.com. Mereka pindah dari Resque dan Redis ke antrean di database, worker mengklaim job lewat FOR UPDATE SKIP LOCKED; v1.0 melaporkan ±20 juta job per hari (HEY), 800 worker, 74 VM, dua datacenter, database antrean terpisah dengan satu primary dan dua replika. Batas: satu produk Rails dengan MySQL; alasan yang mereka tulis adalah kesederhanaan operasi, bukan beban.
- R3-25 Kapan cache salah: Facebook, R. Johnson, "More Details on Today's Outage" (2010-09-23, engineering.fb.com). Klien menganggap error dari database sebagai nilai tidak valid lalu menghapus cache key, query ratusan ribu per detik mencegah database pulih; gangguan ±2,5 jam, lalu traffic dihentikan. Batas: satu insiden 2010, bukan bukti cache buruk; pelajarannya error dari backend tidak boleh memicu invalidasi.
- R3-137 Pool habis karena koneksi ditahan tanpa batas waktu: Val Town, Max McDonnell, "Post-mortem: Exhausted Host Connection Pool" (2024-12-31, blog.val.town, dibuka 2026-10-26). Beberapa query database saling mengunci (deadlock); pool tanpa timeout query, jadi koneksi terkunci menempati slot "permanently"; satu server kehabisan pool, "most requests stalled indefinitely in a pending state"; health check tidak memeriksa database; server dimatikan manual pukul 07.04 ET sesudah laporan user (kejadian mulai 12.15 ET). Perbaikan: health check memasukkan kesehatan pool dan "timeouts to pool queries"; rencana tinjauan agar server yang penuh menolak request. Batas: satu layanan, pemicu deadlock di database, bukan panggilan ke layanan luar

## Untuk NASKAH-3 (temuan yang belum ada di naskah Tahap 2)
1. Pool habis (R3-33): terjadi bila provider notifikasi menggantung ≥ 9–12 detik, bukan lambat 2 detik; lab `t3-bayar` memakai 17 RPS semuanya bayar. Pemicu M harus insiden provider tanpa timeout, atau lab diubah.
2. Beban tidak memaksa cache atau Redis (R3-37, R3-33); alasan Redis masuk adalah rate limit lintas instance (R3-34).
3. Poller outbox tidak boleh memakai kursor `(dibuat, id)` seperti ADR 16 (R3-04): baris terlewat berarti notifikasi hilang.
4. Mode offline lawan ADR 14 (R3-40): akhir pekan 62 jam; batasi bayar tertunda dan umurnya.
5. Dua instance: Caddy bawaan tanpa health check dan retry (R3-13); pin sertifikat dengan masa 200 hari (R3-18); registry `trx` 2 lawan naskah 3 (R3-31).
