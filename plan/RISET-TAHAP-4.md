# Riset Tahap 4 · Integrasi pihak ketiga
Dikerjakan 2026-10-25, skill riset-tahap (hierarki bukti dari analisis-kritis). Semua tautan dibuka 2026-10-25; versi paket dari GitHub Releases (`gh api`), pub.dev, dan pkg.go.dev hari itu. Cakupan dari PROPOSAL "Enam tahap dalam satu tabel" (Tahap 4: batas modul, CODEOWNERS, ADR wajib, gateway, object storage, secret manager, IaC, security review; sengaja belum: memecah semua modul), registry `tahap[3]` (PRD v4: top-up dari bank lewat gateway, verifikasi identitas, QR) dan RISET-TAHAP-3. Stack Overflow ditolak alat pencarian, jadi jebakan diambil dari GitHub issues yang dibuka satu per satu.

- R4-28 Modular monolith: Shopify Engineering, "Deconstructing the Monolith" (2019-02-21). Aplikasi Rails dengan lebih dari seribu developer; pada 2016 tes rapuh dan onboarding berat; mereka memilih modular monolith, bukan microservices; ±6.000 kelas diberi label komponen, tiap komponen punya API publik dan datanya sendiri, alat Wedge menandai pelanggaran. Batas: satu aplikasi Rails, ±70 sampai 100 kali lebih banyak developer dari Tahap 4; alasan yang mereka tulis adalah pipeline dan jaringan per service.
- R4-29 Kapan memecah salah: Segment, "Goodbye Microservices" (2018-07-10). Satu antrean untuk semua tujuan membuat tujuan lambat menahan yang lain (head-of-line blocking). Mereka memecah per tujuan sampai 140+ service (±3 tujuan baru per bulan); beban tiap service beda; library bersama berbeda versi. Digabung jadi satu service; 32 perbaikan library setahun sebelumnya, 46 setahun sesudahnya. Batas: pipeline pengiriman event ke mitra, bukan sistem uang. Pelajaran: isolasi kegagalan pihak ketiga (antrean dan breaker per gateway) tanpa satu service per pihak ketiga.

## Untuk NASKAH-4 (temuan yang belum ada di naskah Tahap 1 dan 2)
1. Webhook ganda (R4-08): duplikat datang dari retry sesudah timeout (Midtrans 15 detik, retry pertama ±2 menit), bukan "dua kali dalam 1 detik".
2. Pemicu memecah (R4-30, R4-31): beban tidak memaksa; alasan harus tim, kredensial gateway, dan audit.
3. Pool habis (R4-32): bila semua transaksi menunggu gateway cukup 3 sampai 4 detik; bila hanya top-up (0,58 per detik puncak) butuh ±35 detik, mendekati timeout 30 detik. Pembayaran QR antar akun adalah posting ledger internal tanpa gateway. Pemicu M harus gateway tanpa timeout, bukan lambat sebentar.
4. Tim (R4-38): pilih satu angka; tiga sumber berbeda.
5. File 365 GB per tahun (R4-35) adalah alasan object storage; foto dan bukti ikut kuota.
